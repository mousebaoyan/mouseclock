# 鼠钟 · 总体设计

> 状态：草案，待评审。表结构见[数据表](data-model.md)，接口见[接口](api.md)。想法的来源和讨论见鼠洞的[征集意见帖](https://bbs.mousebaoyan.cn/t/6771)。

## 1. 目标

- **不漏截止时间**：自动收集各高校学院官网的保研通知（冬令营、夏令营、预推免、九推），整理出截止时间和要点，快到了提醒。
- **盯着发布**：关注的学院一发新通知就提醒，不用等通知出来再去找。
- **信息可信**：每一项都附原文里的那句话；原文删了也有快照；大家一起纠错，每次修改都有记录，能撤销。
- **快**：页面 1 秒内打开，在手机 QQ 里也流畅；筛选、排序、搜索即时出结果；每天抓几百个来源，也不拖慢网站。
- **好接入**：群 bot 每天发一条汇总；用户自己的 Agent 能直接查询、订阅。

暂不做：公众号的通知（第 17 节「以后」）；入营、优营名单和考核结果挂在对应的项目上，用来提醒、补上其中的时间，名单上的人不整理成表。

## 2. 已定决策

| 事项 | 决定 |
| --- | --- |
| 名称 | 鼠钟，暂定，帖子里在征名；出自童谣 *Hickory Dickory Dock* 的 "The mouse ran up the clock" |
| 仓库 | `mousebaoyan/mouseclock`，MIT 许可证；`main` 只能通过 PR 合入 |
| 收录范围 | 先收计算机相关的学院和研究所，第一批先收对四非友好的（如电科、厦大、沈自）；之后按「求收录」的同求人数加 |
| 数据来源 | 以学院和研究生院的官网为准；公众号以后再试，只收官方号 |
| 往年数据 | 也收，可以按届筛选（第 9.1 节） |
| 判别 | 先调用 System One 判别接口（比如 Jev 官方的接口）初筛，通过的再交给 LLM 抽取；模型和门槛见第 8.1 节 |
| 账号 | 不单独注册，用鼠洞账号登录；等级、角色、禁言和冻结都以鼠洞为准 |
| 访客 | 只能看几条预览，登录后看全部 |
| 提醒 | 邮件发到 `QQ号@qq.com`：订阅的项目截止前 3 天提醒，关注的学院有新通知就提醒；群 bot 每天发一条汇总 |
| 纠错 | L3 以上直接修改、审核申请，L3 以下提修改申请；每次修改都有记录，能撤销 |
| Agent | 提供 MCP 服务和 API，用个人令牌登录；Agent 不能直接修改数据，也不能审核 |
| 部署 | 网站和抓取分开：网站放在香港的服务器上，和鼠洞同一台；抓取、初筛和抽取放在上海的机器上，访问学院官网更快，也不占网站服务器的资源。两边只通过接口交接（第 16 节） |
| 技术栈 | 网站和鼠洞同一套（TypeScript、React Router、Hono、Kysely），抓取节点用 Python，数据库用服务器上的 PostgreSQL 18（第 5 节） |

## 4. 架构

```text
抓取节点（上海）
  │  领活 → 抓列表页、正文和附件 ──▶ 学院、研究生院官网（通用 / 配置 / 浏览器 / 专用适配器）
  │  整理成快照 → 初筛：判别模型看标题 → 抽取：LLM 按字段输出，每项附原文证据
  ▼  HTTPS：抓取节点主动连接，用抓取节点令牌
网站（香港，和鼠洞同一台服务器）── 数据库：1Panel 的 PostgreSQL
  ├─ 收结果：存通知和快照，归并成项目和版本，拿不准的进审核页
  ├─ 网页 / API / MCP ◀── 浏览器、用户的 Agent
  ├─ 登录 ──▶ 鼠洞（授权方）
  ├─ 邮件 ──▶ 订阅和关注的提醒
  └─ 群汇总 ◀── AstrBot 插件每天来取
```

- **两个部署单元**：抓取节点负责抓取、初筛和抽取，网站负责其余的一切。两边只通过[抓取节点接口](api.md#6-抓取节点)交接，不共享数据库，可以用不同的语言，各自部署、各自升级。
- **抓取节点不存业务数据**：要抓什么、哪些通知已经见过，都问网站；抓完把结果交给网站。网站连不上时这一轮就等着，下一轮再来。
- **只有抓取节点主动连接**：网站不连抓取节点，抓取节点放在内网也行，只要能访问外网。
- **一套业务逻辑**：网页、API 和 MCP 调用同一组服务函数，权限、订阅上限和修改记录只有一套。
- **不直接连 QQ**：群汇总由 AstrBot 插件定时来取，和鼠洞的做法一样；鼠钟不反向连接插件。

## 5. 技术选型

评判标准：
- 模型写这门技术写得准不准；
- 类型检查快不快、严不严；
- 版本稳不稳；
- 实测性能；
- 优先选主流的；服务器上已有的（1Panel 的 PostgreSQL、Redis）能复用就不加新服务。

### 5.1 选定的方案

| 部分 | 选定 | 理由 |
| --- | --- | --- |
| 网站 | 和鼠洞同一套：TypeScript 7、Node 26、React Router 8、Hono 和 `@hono/zod-openapi`、Kysely、Tailwind CSS 和 shadcn/ui；pnpm、oxlint、Prettier、Vitest、Playwright | 登录、邮件、界面风格和写法都能照搬。选型依据和框架的实测见[鼠洞的总体设计 §5.2](https://github.com/mousebaoyan/mousehole/blob/main/docs/design.md#52-选型依据) |
| 数据库 | 服务器上 1Panel 的 PostgreSQL 18 | 和鼠洞共用实例，不加新服务 |
| 抓取节点 | Python 3.14，uv 管依赖；Ruff 做 lint 和格式化，Pyright 的严格模式做类型检查，pytest 做测试 | 浏览器抓取、正文提取、PDF 和 Office 解析、中文的文字识别，Python 的库最全，代价是多一套工具链。3.15 刚发布，文字识别要用的 onnxruntime 还没有它的安装包。Pyright 和 VS Code 的 Pylance 是同一个引擎，编辑器里看到的错误和 CI 一致 |
| 抓取 | httpx（异步）请求网页，Playwright 驱动浏览器（Chromium 的无头精简版），lxml 按 CSS 或 XPath 取出列表 | 各自领域的主流库 |
| 正文、附件和文字识别 | 正文按建站系统的模板用 lxml 取；pypdf 读 PDF，python-docx 读 `.docx`，legacy-doc 读老的 `.doc`，openpyxl 读 `.xlsx`，xlrd 读 `.xls`；文字识别候选 RapidOCR | 都关在 `parse` 模块里，换了不影响别处。正文和附件用真实的通知和附件比较后定，结果见第 5.2 节；文字识别在[文字识别](https://github.com/mousebaoyan/mouseclock/issues/47)的任务里定。不用 AGPL 许可的 PyMuPDF |
| 接口的类型 | 网站用 Zod 写接口的定义，生成 OpenAPI 文档；抓取节点从这份文档生成 Pydantic 模型 | 两边语言不同，接口的类型也只有一个来源。抓取节点用 Pydantic 校验网站的返回和模型的输出 |
| 判别接口和 LLM | System One 的 SemIf；DeepSeek 官方接口的 V4.1 Flash（`deepseek-flash`），按编号抽取 | 判别见第 8.1 节，抽取比较见第 8.5 节 |

### 5.2 实测

测试机：AMD Ryzen 7 8845HS，Chromium 156（Playwright 1.64），Python 3.14。

**总表一次发给浏览器**（第 14 节）：造一年的项目（200 所学校、600 个学院），只带总表要用的字段；在 Chromium 里解析，按全部筛选条件和关键词筛一遍，再按截止时间排序。手机用 CPU 降速模拟。

| 项目数 | JSON | gzip | Brotli（质量 5 / 11） | 降速 6 倍：解析 + 筛选排序 |
| --- | --- | --- | --- | --- |
| 1000 | 401KB | 62KB | 54KB / 42KB | 3.7ms + 1.3ms |
| 3000 | 1045KB | 165KB | 138KB / 105KB | 8.5ms + 3.8ms |
| 6000 | 2009KB | 321KB | 265KB / 200KB | 14.9ms + 9.3ms |

CPU 不是问题，要省的是带宽，做法见第 14 节。

**浏览器抓取**：用 Chromium 的无头精简版，不加载图片、字体和音视频。

| 测了什么 | 结果 |
| --- | --- |
| 内存（浏览器加 Playwright 的驱动） | 空载约 210–240MB；开一个页面峰值 370–450MB，看页面大小；同时开两个列表页约 410MB。完整版 Chromium 的无头模式空载就要 330MB，峰值 520MB |
| 厦大信息学院的列表页 | 浏览器 0.7 秒；普通请求 0.22 秒、39KB，标题都在 HTML 里，用不着浏览器 |
| 电科计算机学院 | 用了瑞数的反爬：先返回 202 和一段脚本，脚本设好 Cookie 后重新请求。Playwright 默认带着自动化标记（`navigator.webdriver` 为真），无头模式的 UA 里写着 `HeadlessChrome`，有一处就返回 400；关掉自动化标记、UA 里写成 `Chrome` 就能通过，UA 末尾照样写明鼠钟。首页 3.1 秒，内存峰值约 425MB；同一个会话里再开列表页，不用再过挑战 |

**正文和附件**（2026-11-09）：45 个来源各取 2 条最新的通知，加上中科院几个所的 7 条，共 97 页；从中下载 35 个附件，PDF、Word、Excel 都有。

| 测了什么 | 结果 |
| --- | --- |
| 取正文 | trafilatura 遇到正文只有一个嵌入 PDF 的页面（东南大学的 WebPlus）、正文是一张图片的页面（北邮），会把导航和页脚当成正文；找「文字最多的一块」，83 页里有 19 页认成了页脚或翻页。按建站系统的正文容器取（博达、WebPlus、TRS、GPower，加上北科研究生院和国科大的几种），97 页都认得出 |
| PDF | pypdf 和 pdfplumber 在 8 个 PDF 上取出的汉字一个不差；pypdf 把表格的一行留在同一行，pdfplumber 会把折行的单元格拆开；pypdf 快两三倍（89 页 0.97 秒对 2.89 秒，Apple M4）。东南大学的两个 PDF 把常用字映射成样子相同的康熙部首（「⽣」代替「生」），取出后换回常用字 |
| Word | python-docx 按段落和表格的顺序取 `.docx`，表格一行一行，横向合并的单元格只取一次。90 页通知里的 90 个附件链接（不算正文里的图片）有 26 个是老的 `.doc`，多是申请表：legacy-doc（纯 Python，MIT 许可）读的 7 份里，6 份和 LibreOffice 导出的汉字一致，剩下一份 LibreOffice 丢了整张表格，它取全了。它没带类型标注，`crawler/typings/` 里补了用到的部分。另一种做法是镜像里装 antiword（2005 年后没人维护）或 LibreOffice（几百 MB） |
| Excel | openpyxl 读 `.xlsx`，xlrd 读 `.xls`，样本里各 1 个都没问题 |
| 下载 | 7 次拿到的不是文件，是博达的「请输入验证码下载附件」页面（北科计通、厦大、电子科大信通、国科大杭州等）；先打开通知页、带着来源页下载也一样，是网站的设置。按第 7.2 节不破解：附件照样列出，文字留空，不存文件 |

**文字识别**：RapidOCR（PP-OCRv6）识别一张 20 行的中文页面约 1 秒，进程峰值约 690MB；抓取节点只有 4 核，会慢几倍。

抓取节点同时开 2 个浏览器页面、一次识别一张图，峰值约 1.4GB，3.6GB 内存够用（第 16 节）。

## 6. 账号与权限

### 6.1 登录

- 用鼠洞账号登录，鼠洞做授权方，按 OAuth 2.1 授权码流程加 PKCE，步骤见[接口 §2](api.md#2-鼠洞登录)。鼠钟是鼠洞登记的自家应用，不弹授权确认。
- **自动登录**：没有鼠钟会话的人打开页面时，鼠钟把浏览器带到鼠洞。已经登录鼠洞的，鼠洞直接带着一次性凭证跳回来，不用点；没登录鼠洞的回来按访客显示，点「登录」再走鼠洞的登录。
- **不共用 Cookie**：鼠洞的会话只发给 `bbs.mousebaoyan.cn`，鼠钟用自己的会话。这样鼠钟出了问题，也拿不到鼠洞的会话。
- **拿到的资料**：鼠洞的用户 ID、名字、头像、等级、角色、禁言和冻结状态，以及 QQ 号（只用来发邮件，不显示）。每次登录时更新，登录期间每小时从鼠洞刷新一次，所以在鼠洞被禁言、冻结或者降级，最多一小时后在这里生效；被封禁的，鼠洞那边的令牌失效，鼠钟让他退出。
- 鼠洞的授权接口见鼠洞的[接口 §8.3](https://github.com/mousebaoyan/mousehole/blob/main/docs/api.md#83-oauth-授权)。本地开发和测试用假的鼠洞，也可以对着本地跑的鼠洞（[开发约定 §5](development.md#5-测试)）。

### 6.2 权限

| 谁 | 能做什么 |
| --- | --- |
| 访客 | 看总表的前 5 条预览 |
| 成员 | 看全部；订阅、关注、记报名、贴学院标签、反馈、提修改申请、求收录、生成个人令牌 |
| L3 及以上 | 以上都能，还能直接修改、审核修改申请、标记已核对 |
| 管理员 | 以上都能，还能复核争议、删除项目、撤销某人的全部修改、收回某人的修改权限，管来源、院校清单和学院标签的预设 |
| 站长 | 系统设置：发信邮箱、抓取节点令牌 |

- 成员就是鼠洞的成员，也就是在群里的人。冻结的按访客算；禁言的能看、能订阅关注、能记报名，其余都不能做。
- 鼠洞的管理员和站长，在这里也是管理员和站长。
- 管理员可以单独收回某人在鼠钟的修改权限，不影响他在鼠洞的权限。

## 7. 抓取

### 7.1 来源

- 一个来源是一个通知列表页，比如学院官网的「通知公告」、研究生院的「招生信息」。一个学院可以有几个来源。
- 来源由管理员接入。群友在「求收录」里给的链接只当线索（第 10.1 节）。
- 接入时往回翻页，补上前两年的通知，作为往年数据。

### 7.2 怎么抓

| 方式 | 用在哪 | 接入要做什么 |
| --- | --- | --- |
| 通用抓取 | 列表页规整的，希望是大多数 | 只填通知列表页的地址 |
| 配置 | 结构特殊的 | 几行配置，指明列表、标题、日期和翻页在哪 |
| 浏览器抓取 | 要执行 JS 才能看到内容的 | 用浏览器打开再抓 |
| 专用适配器 | 前三种都不行的极少数网站 | 单独写代码 |

- **按建站系统做模板**：不少高校官网用的是同几家建站系统，一个模板能管一批。通知的正文也按建站系统的正文容器取；哪个系统都对不上的，这条通知记成「认不出正文」，补上那个系统的模板，不猜哪一块是正文。
- **LLM 只在接入时用**：管理员在网站上填好列表页的地址，点「试抓」；抓取节点下一次领活时领到它，抓下来，让 LLM 认出列表、标题、日期和翻页在哪，把抓到的条目和生成的配置交回网站。管理员看过没问题再保存；之后每天按配置抓，不再问 LLM。
- **试抓的流程**：管理员在来源管理页的表单里填好网址（以及要不要浏览器、已有的配置），点「试抓」，网站记一条试抓；页面显示「等抓取节点」，每隔几秒刷新，直到抓取节点交回结果。结果列出抓到的条目（标题、链接、日期）和生成的配置，失败的写原因。管理员看过点「采用」，网址、要不要浏览器和生成的配置填回表单，再保存来源：采用就是保存来源，配置改前改后记进操作日志；发起试抓也记一条。
- **不硬闯**：要登录才能看的、有验证码的不抓，标成「暂时抓不了」并写明原因。只要求用浏览器打开的脚本挑战（比如瑞数的反爬）不算：页面是公开的，人用浏览器打开就能看，浏览器抓取按[开发约定 §2](development.md#2-抓取和判别)的设置通过，UA 照样写明鼠钟。
- **已经遇到的**：电科计算机学院的官网用了瑞数的反爬，要用浏览器抓取（第 5.2 节）；浙大计算机学院的 HTTPS 连不上，只能用 HTTP，要写进配置。

### 7.3 频率和礼貌

- 平时每个来源每天抓 2 次；3–9 月和 12–1 月是旺季，每 4 小时一次。
- 同一个网站同一时间只发一个请求，两次请求之间隔 5 秒；请求头写明是鼠钟，附上联系方式。浏览器的一次页面访问算一个请求。
- 不读 robots.txt：抓的都是公开的通知列表，礼貌靠上面这几条保证；有的学院官网一请求 robots.txt 就断开连接（比如西电），照它的规矩反而一页都抓不了。
- 失败了等下一轮再抓，一轮里不反复重试。

### 7.4 发现变化

- **新通知**：列表里出现没见过的链接，直接比网址。
- **正文变化**：还没截止的项目，每天重抓一次它的通知，在它的来源那一轮里一起抓；正文的文字和上一份快照不同，就存一份新快照，再交给抽取。
- **删除**：重抓时通知打不开（404、410），标成「原文已删除」，快照照样能看。从列表里消失不算：列表会翻页，旧通知本来就会被挤下去。
- **附件**：正文里和正文旁附件区里的文件（PDF、Word、Excel、压缩包），以及正文里的图片，按出现的顺序下载下来、解析出文字；图片做文字识别，压缩包不取文字。附件和正文一起存进快照。下载不成的（比如要验证码才能下载），照样列出名称和网址，文字留空。

### 7.5 抓取看板

- 记下每个来源每一轮的结果：成功还是失败、失败原因（超时、403、找不到列表）、列表里有几条、新通知几条、其中有用的几条，以及 LLM 用了多少 token。
- 连续 2 轮失败的标红；旺季里 30 天没有新内容的标黄，往往是网站改版了，配置抓不到东西。
- 登录后都能看。
- 按天看（北京时间，默认今天），列出这一天抓过的来源，标红、标黄的排在前面：
  - 每个来源一行：学校、学院和栏目，这一天各轮的结果，没抓成的通知能展开看网址和原因，以及这一天的用量。
  - 标红：到这一天为止最近的 2 轮都没读到列表。标黄：这一天在旺季（3–9 月、12–1 月），这个来源 30 天里没有新通知（按第一次见到的时间）。
  - 最上面是这一天按用途和模型的总用量，以及抓取节点上次来领活的时间：抓取节点每分钟来一次，超过 10 分钟没来就提示。
- 来源管理页上每个来源的最近一次结果，链接到那一天的看板，只看这个来源。

## 8. 判别与抽取

### 8.1 初筛

- 新通知先由 SemIf 判别模型只看标题，门槛为 0.1，判断是不是保研招生相关的通知：冬令营、夏令营、预推免、九推的报名通知，它们的补充、延期通知，以及入营、优营名单和考核结果。
- 调用 System One 判别接口，比如 Jev 官方的接口：对带类型的问题（是否、单选、打分）一次给出校准过的概率，快而便宜。[OneJev](https://github.com/OmniJev/OneJev) 兼容同一种接口，需要时也能自己部署；换哪家只改配置。
- 门槛宁低勿高：漏掉一条通知的代价，比多调一次 LLM 大得多。
- 用 `crawler.screening.evaluate` 在标注集上取零漏检的最高门槛，再向下留余量并写明幅度：SemIf 从 0.133 取 0.1，留 0.033。换模型时门槛一起重定，标注集扩充后也重跑。
- 判别接口不可用时，这一轮的初筛等着，不跳过初筛直接送给 LLM。
- 鼠洞的 bot 插件试过用 OneJev 筛群聊：有内容的和闲聊的分数混在一起，定不出门槛。通知标题短而规整，预计会好很多，但要用实验证明（第 8.5 节）。

### 8.2 抽取

程序能取的先由程序取：正文和附件的文字按句编号，日期的写法找出来、换算成时间值，链接和邮箱也都编上号。模型只做程序做不了的判断，比如通知涉及哪几个项目、哪个日期是报名截止、哪个链接是报名入口：它从编号里选，证据写句子的编号，原文由程序取出。

抽取前，网站给出这所学校在院校清单里的学院和近期的项目（编号、学院、届、类型、名称、报名时间），模型对照着认。一条通知的抽取结果是它涉及的项目，一个都没有就是无关：

| 项 | 说明 |
| --- | --- |
| 项目 | 是已有的哪个项目，给出编号；没有就新建 |
| 学院 | 从院校清单里选。联合举办的归发通知的学院，全校统一的归研究生院 |
| 届 | 见第 9.1 节 |
| 类型 | 冬令营、夏令营、预推免、九推，归类见第 9.1 节 |
| 名称 | 照通知的写法，比如「2026 年“智能与网络”夏令营」「推免预报名（第二批）」 |
| 作用 | 这条通知对这个项目是报名（招生简章、报名通知、实施细则）、补充（延期、更正、补充说明），还是名单（入营、增补、优营、复试、拟录取名单，以及和名单一起发的安排） |
| 字段 | 通知里写了的字段，见下表 |

- **项目怎么分**：有自己报名时间的一批报名是一个项目，第二批、增补报名都单独算；报名只有一次、复试分几批的，还是一个项目。分方向或分营的，报名时间各不相同就各算一个，共用一次报名就算一个，方向写进招收专业。
- **一条通知可以涉及几个项目**，比如研究生院的一条通知里有几个学院各自的夏令营，或者优营名单和预推免报名发在一起。

| 字段 | 键 | 值 |
| --- | --- | --- |
| 报名时间 | `apply` | 开始 `start`、截止 `end`，都是时间值；额满即止、先到先审的加上 `"rolling": true`。截止是完成报名的最后时间：网上报名或者发送材料，以通知里主要的那一步为准，别的截止写进其他时间 |
| 报名入口 | `apply_url` | 报名系统的网址；发邮件报名的写 `mailto:` 地址 |
| 活动时间 | `event` | 开始 `start`、结束 `end`，都是时间值，只有一天的两个相同；线上 `online`、线下 `offline` 还是都有 `hybrid`，写在 `mode`；地点 `place`。夏令营是营期，推免是复试或考核 |
| 其他时间 | `dates` | 材料截止、导师推荐、公布名单、确认参加等，每项有名称 `label` 和 `start`、`end` |
| 招收类型 | `degrees` | 硕士 `master`、直博 `direct_phd`，可以都有 |
| 招收专业 | `majors` | 专业或方向，一条一项，照原文 |
| 报名要求 | `requirements` | 排名、外语成绩等，一条一项 |
| 要交的材料 | `materials` | 申请表、成绩单、推荐信等，一条一项 |
| 考核方式 | `assessment` | 笔试、机试、面试等，一条一项 |
| 名额 | `quota` | 照原文，比如「100–150 人」 |
| 待遇 | `benefits` | 路费、住宿、补贴等，一条一项 |
| 联系方式 | `contacts` | 邮箱、电话、QQ 群，一条一项 |

- **分段活动**：共用一次报名的项目，`event` 从最早的开始写到最晚的结束，线上线下都有的写 `hybrid`，中间各段的时间不用另标。
- **营期范围**：夏令营的 `event` 以通知写的营期为准；宣讲、科研实践等另列时间的环节写进 `dates`，不扩展营期。
- **活动时间的精度**：「9 月 19–20 日择期」按这两天的区间写；只给一个活动时间（如「9 月中旬面试」）时，`start` 和 `end` 写同一个时间值；只给最后一批时间时只写 `end`，只写「几点开始」「几号报到」时只写 `start`，不补另一端。
- **滚动报名**：「随时报、随时面、随时录」按先到先审处理，在 `apply` 中加 `"rolling": true`，截止仍照原文写。

- 每个字段附上证据 `evidence`：原文里支撑它的一句或几句，每句写成 `{"quote": "…"}`，在附件里的加上附件在快照里的序号 `attachment`（从 0 开始）；再给一个 0 到 1 的置信度 `confidence`。
- 只给通知里写了的字段，写着「另行通知」的也不给。后来的通知没提到的字段，保持原来的值（第 8.4 节）。
- 附件（申请表模板等）不算字段，详情页直接列出快照里的附件。
- 字段以后可以加，加的时候在这张表里写明值的格式。
- 原文明示了时间、程序却没有对应的日期候选时，模型照抄时间文字并选证据句子编号，交到项目的 `unresolved_dates`，包含目标 `field`、原文 `text` 和程序还原的 `evidence`。目标为 `apply.start`、`apply.end`、`event.start`、`event.end` 或 `dates`，同一端点不同时交推测的换算值。原文没写或另行通知不算未识别时间。
- 学院与已有项目从网站提供的清单中选编号；已有项目的学院、届和类型须与对照一致。对照中的旧时间不作为当前通知的日期候选或证据。

**时间值**：原文写到哪一步就记到哪一步，不替原文补全，都是北京时间。

| 原文 | 时间值 |
| --- | --- |
| 6 月 30 日 23:59 | `{"date": "2026-06-30", "time": "23:59"}` |
| 9 月 19 日 24 点 | `{"date": "2026-09-19", "time": "24:00"}` |
| 6 月 30 日 | `{"date": "2026-06-30"}` |
| 6 月 22 日前 | `{"date": "2026-06-22", "mark": "before"}` |
| 7 月 3 日前后、左右 | `{"date": "2026-07-03", "mark": "about"}` |
| 7 月上旬、中旬、下旬；月初算上旬，月底算下旬 | `{"month": "2026-07", "part": "early"}`，`mid`、`late` |
| 7 月 | `{"month": "2026-07"}` |

- 日期的数字可以用阿拉伯数字或中文数字，比如「二〇二六年六月三十日」「九月中旬」。「号」和「日」等价。完整年月日也接受 `2026-06-30`、`2026/6/30`、`2026.6.30`，同一日期的数字分隔符一致，中间不带空格。数字日期也能带时刻，比如 `2026-6-1 17:00`。
- 日期在括号内、时刻紧跟在括号外时一起识别，比如「（6 月 30 日）17:00」。
- 数字分隔的年月日须包含完整年份。`6.30`、`6/30`、`6-30` 这样的短数字月日按普通文字保留，不论前后写了什么。原文明示的未识别时间走前述 `unresolved_dates` 交接流程。
- 日期与时刻的识别以同一行内的表达式为界，表格跨行的日期和时刻分别保留，同日第二段时间保持原文。
- 日期范围的首端可省略日/号，比如「六月一至三十日」「十二月二十八至一月十日」。没写年份的先按发布年份算，比发布日期早半年以上的算下一年：12 月发的通知写「1 月 10 日截止」算下一年，回顾 7 月的夏令营仍算当年。时间段右端没写的年月跟左端，跨年同样按这条。「即日起」是发布那天；发布日期为空时，要靠它推年份的不给时间值。
- 换算成时刻（排序、倒计时、状态和提醒用）时，拿不准的往早里算：只写到日的截止算到当天结束，带 `mark` 的算到前一天结束，只写到旬或月的算到这段时间开始；开始都从最早的可能算起。页面上照原文的写法显示，不显示换算出的时刻。

### 8.3 校验

网站收到抽取结果时检查，过不了的进审核页，由人判断：

- 证据要能在快照里原样找到：在标明的正文或附件的文字里找，只忽略空白的差别。找不到的字段不上表。
- 项目编号要是抽取前给出的项目之一，学院要在这所学校的院校清单里。
- 明显不对的：截止早于发布时间，届不在发布那年到后两年之间。
- 作用是报名、却没有报名截止的，确认原文确实没写。
- 置信度低的字段，审核通过才上表。
- 未识别时间的文字及证据在原文中核对后，以 `unparsed_date` 进入审核页，其他确定字段照常处理，对应的旧时间保持不变。审核者在项目页补充时间，再关闭条目；关闭条目本身不会把原文文字换算成时间，也不会覆盖旧值。已有项目即使有旧截止，延期中的新时间未识别也必须入队；同一快照重复交结果不重复入队。

### 8.4 归并与版本

归并在网站上做：要看已有的项目和人工改过的值，这些都在网站的数据库里。网站不调用模型，认项目靠抽取给出的编号。

- 一条通知涉及几个项目，就给每个项目各加一个版本：给了编号的加到那个项目上，没给的新建项目。同一学院、同一届、同一类型已经有项目时，新建的在审核页标出来，由人确认不是重复的。
- 版本只带通知里写了的字段：带了的换成新值，没带的保持原样。报名时间和活动时间按开始、截止这些部分合并，比如延期通知只写了新截止，就只换截止，开始照旧；其他时间按名称合并，同名的换成新的，没有的加进去。和原来的值逐个比较，变了的记下来；截止时间变了，订阅的人收到邮件（第 11 节）。
- 名单类的版本通常只带时间，比如入营名单里定下的活动日期、复试名单里的确认截止；名单上的人不整理成表。
- 人工改过的字段不会被抓取覆盖。新版本的值和人工改的值不一样时，进审核页。

### 8.5 实验

- 从第一批来源抓真实的通知，做成标注集：初筛用标题和标注，抽取用正文和各字段的正确值。标注集只放网址、标题和标注，全文和快照不进仓库。
- 初筛看召回率（有没有漏），以及能挡掉多少无关的通知；拿关键词规则当基线比一比。
- 抽取看各字段的准确率，重点是截止时间。
- 改模型、提示词或门槛，都要在标注集上重跑一遍，结果贴在 PR 里。

### 8.6 成本

- 初筛挡掉大部分通知；每条通知只抽取一次，正文变了才再抽。
- 每次调用都记下用量，按天汇总显示在抓取看板上。
- LLM 请求按可复用的前缀组织：固定规则与输出结构在前，同一所学校的学院清单和近期项目其次，单条通知的标题、发布日期和编号正文最后。结构化数据使用固定字段顺序，共用部分不加入当天日期、请求编号等易变内容；后续试抓等调用也遵守这条规则。
- DeepSeek 官方 Responses API 自动管理前缀缓存，命中量取 `usage.input_tokens_details.cached_tokens`。实验报告保留输入、输出和命中 token，按实际命中计算费用；接口没返回用量或命中数时记为未知，不当作零或免费。
- 估算：旺季每天几十条通知进 LLM，用便宜的模型，一天花不了几块钱。

## 9. 内容

### 9.1 学校、学院和项目

- **学校**：名称、简称和层次。简称可以有几个（北大、PKU），只用来搜索，页面上不显示。层次只记最高的一个：C9 都是 985，985 都是 211，211 都是双一流，记了 C9 就不再记 985；按层次筛选时，选 211 只出现最高是 211 的学校，没有层次的归「其他」。校徽让人一眼认出是哪所学校，项目卡片、院校清单、学院页和项目页上学校名的旁边都有；由管理员上传，存在鼠钟、由鼠钟提供，不从学校的网站去拿，还没有的显示校名的第一个字。
- **学院**：泛指招生单位，包括学院、研究所和研究生院，属于一个学校（中科院的研究所属于中国科学院大学，和研招网上的招生单位一致）。地区记在学院上，是学生就读的地方：深圳校区、中科院的研究所和学校不在一地。院校清单里的学院不一定已经接入来源，没接入的也能关注。
- **项目**：一个学院面向某一届的一次招生活动，分批报名的每批算一个（第 8.2 节）。字段见第 8.2 节，每个字段有值、证据和来源的版本。
- **届**：本科毕业、研究生入学的那一年，和大家说的「27 届保研」一样，按届筛选就能看到这一届能报的全部项目。2026 年的夏令营、预推免和九推是 2027 届，2026 年 12 月到 2027 年 1 月的冬令营是 2028 届。标题里的年份不一定是届：夏令营常写举办的年份，推免常写入学的年份。
- **类型**：冬令营、夏令营、预推免、九推。各校的叫法不同，这样归类：暑期学校、学术交流营、科学营、开放日算夏令营；学校叫预推免、预报名、提前选拔的推免算预推免，比如电科的「优本计划」；正式的推免招生（招生简章、推免说明）和推免服务系统开放后的补录算九推。普通博士的申请考核、录取后的体检和入学通知、只招已录取博士生的营都不收。
- **状态**：按时间算出未开始、报名中、已截止；另有「已核对」和「有争议」两个标记。

### 9.2 已核对

- L3 以上或管理员核对过一个项目的全部字段后，标记「已核对」，记下是谁、什么时候核对的。
- 之后有新版本改了字段，或者有人修改了项目，标记取消，等再次核对。

### 9.3 学院标签

- 公开的标签贴在学院上，不随某一年的通知走，往年的评价也算数。
- 只能从管理员预设的标签里选，比如「对双非友好」「卡本科出身」「看重科研」「看重竞赛」「有机试」。用词要中性，不用「歧视」这类字眼，免得引战。
- 每人每个标签一票，可以撤回。页面上只显示人数，不显示是谁，但记录里有。
- 总表可以按标签筛选。
- 乱贴的标签管理员可以删，删除也有记录。

### 9.4 我的报名

- 每人可以给任何项目记进度：想报、已报名、已交材料、入营、优营、放弃，另外可以写一段备注。
- 只有自己看得到，不占订阅名额。

每个项目旁有「反馈」按钮，有两种用法：

- 只说这条有问题：写明哪里不对；
- 给出改成什么：这就是修改申请，要写理由、附依据（原文链接或截图）。

L3 以上可以不提申请，直接修改，同样要写理由、附依据。两种反馈都算进争议的人数。

### 12.2 审核

- L3 以上在审核页处理修改申请：通过就按申请修改，驳回要写理由。申请人在「我的」里能看到结果。
- 抽取拿不准的字段、拿不准的归并、和人工改过的值冲突的新版本，也都在审核页处理（第 8.3、8.4 节），按种类分开列，每条看得到原文的证据和抽出来的值。通过的效果如下；驳回只关掉这一条，什么都不改。

| 待审的 | 通过 |
| --- | --- |
| 证据找不到、置信度低、明显不对的字段 | 照抽出来的值上表，来源记为那个版本，之后的通知照常更新它；值变了的记进那个版本改了的字段 |
| 和人工改的值冲突的字段 | 同上：新版本的值替换人改的值 |
| 编号或学院对不上、届不对的项目 | 审核的人从这所学校的项目里选对的那个，或者选对它的学院、届和类型新建一个，再照收抽取结果时那样归并（第 8.4 节） |
| 可能重复的新项目 | 不是重复的就保留；是重复的，选出原来的那个，把这个项目的各版本按顺序并进去，再删掉这个，它其他待审的条目一起关掉。有人改过它的字段的，先撤销那些修改再并，并进去以后到原来的项目上重做；两个项目有同一条通知的版本的，并不了 |
| 报名通知没有截止 | 确认原文确实没写；原文写了的，去详情页改报名时间 |
| 原文时间无法识别（`unparsed_date`） | 核对日期原文和证据，去项目页补充时间后关闭条目；关闭本身不换算原文、不覆盖旧时间 |

- 字段的条目旁边写着这个字段现在的值和来源：之后有更新的通知或者人改过的，审核的人比一比再决定。
- 每次审核记进操作日志，条目上记下谁、什么时候处理的，通过还是驳回。

### 12.3 争议

- 3 个不同的人反馈同一个项目有问题（修改申请也算），这个项目自动标上「有争议」，排到审核页最前面。
- 管理员复核：改正，或者确认没错，然后取消标记；之后的反馈重新计数。
- 有争议期间提醒照发：万一信息其实没错，停了提醒反而会让人错过截止。

### 12.4 记录和撤销

- 每次修改、审核、标记已核对和复核争议，都记下谁、什么时候、通过网页还是 Agent、改了哪个字段、改前改后的值、理由和依据。
- 登录后都能看记录：每个项目的详情页有它的修改记录，审核页有全站的「最近修改」。
- **修改**：一次改一个或几个字段，或者项目的名称、届、类型。报名时间、活动时间和其他时间按部分记，只改了截止就只记截止，没改的部分照常由之后的通知更新。人改过的字段之后的通知不覆盖，新值不一样时进审核页；清空了的也一样，之后的通知不会把它加回来。
- **撤销**：任何一次修改都能一键撤销，撤销本身也记下。字段回到修改前的值，连同来源：原来来自哪个版本，就回到那个版本，之后的通知照常更新它；原来是更早的一次修改设的，就还是人改的；原来没有的，就去掉。字段现在的值还来自这次修改才能撤销；之后又有人改过（哪怕改回同样的值）或撤销过的，先撤销后来的那次，免得把别人的修改悄悄冲掉。
- 管理员可以一次撤销某人的全部修改，并收回这个人的修改权限：从最近的一次往前撤，之后又被别人改过的留着不撤。
- 管理员的其他操作，比如接入和修改来源、删除项目、改权限、改标签预设、改系统设置，都记进操作日志。

## 13. Agent 接入

- **MCP**：提供 MCP 服务，支持 MCP 的 Agent（Claude Code、Codex、Cursor 等）加一行配置就能用。MCP 是接口的薄包装：工具由接口的定义生成，不单独写一套，见[接口 §4](api.md#4-mcp)。
- **API**：开放 API，附 OpenAPI 文档；登录后可以下载全部数据。网站根目录放 `/llms.txt`，说明网站和接口怎么用。
- **个人令牌**：在「我的」里生成，可以选权限范围：只读，或者再加上个人操作（订阅、关注、报名记录、反馈和修改申请）。令牌随时可以作废，库里只存 SHA-256。
- **不能做的**：直接修改、审核和管理只能本人在网页上做。
- **记录和限制**：通过令牌做的操作，记录里标明「通过 Agent」；每个令牌单独限制请求频率。

## 14. 性能与资源

目标见第 1 节，实测见第 5.2 节。

- 一年的项目一次发给浏览器，筛选、排序、搜索都在浏览器里做，不用每次问服务器；往年的按需再取。3000 个项目压缩后约 100–140KB，手机上解析加筛选不到 15 毫秒，所以要省的是带宽：首屏由服务端渲染，不等这份数据；只发给登录的人；数据变了才重新生成、预先压缩，没变时浏览器用缓存。
- 页面由服务端渲染，首屏不等脚本。
- 页面和接口只带用得上的字段。
- 抓取、初筛和抽取在抓取节点上跑，不占网站服务器的 CPU 和内存。抓取节点交来的快照和附件是网站服务器的入站流量，不占出口带宽。
- 网站服务器的出口带宽只有 25Mbps，和鼠洞等服务共用，页面大小按鼠洞的预算来。
- 压缩照鼠洞：服务器上的 OpenResty 不压缩，页面和接口由应用自己压缩（`platform/compress.ts`），浏览器支持 Brotli 就用 Brotli，否则用 gzip；JS 和 CSS 在构建时预先压缩（`scripts/compress-assets.ts`），文件名带内容哈希，永久缓存。
- 校徽每张不超过 16KB：一页卡片有二十来个校徽，每个只显示几十像素。

## 15. 安全与隐私

- 会话和个人令牌是高熵的随机值，库里只存 SHA-256。
- QQ 号只用来发邮件，页面和接口都不显示。
- 订阅人数和学院标签只显示人数；报名记录只有本人能看。
- 交给 LLM 和判别模型的只有公开的通知内容，不带任何用户的数据。
- **最小权限**：抓取节点只有抓取节点令牌和模型的 key，拿不到用户的数据；网站没有模型的 key。抓取节点令牌只能调[抓取节点接口](api.md#6-抓取节点)，库里只存 SHA-256。
- **外部内容当作数据**：网页、附件和模型输出都不可信。快照显示前按白名单净化，只留文字、表格和链接，不执行其中的脚本，也不显示图片：显示就会让每个读者的浏览器都去学院的网站加载；附件只作为下载返回，不在浏览器里打开；通知里的文字只作为要读的材料交给模型，写在提示词里的指令和它分开，通知里写的「指令」不起作用。
- 抓取遵守第 7.3 节；不抓要登录才能看的内容，不破解验证码。
- 快照只给登录的人看，始终链接回原文。
- 页面上的站外链接（原文、报名系统）加 `rel="nofollow noopener"`。

## 16. 部署与运维

| 部分 | 放在哪 | 说明 |
| --- | --- | --- |
| 网站 | 香港的服务器，和鼠洞同一台 | 容器部署，前面是 1Panel 的 OpenResty；数据库用服务器上 1Panel 的 PostgreSQL |
| 抓取节点 | 上海的机器：4 核、3.6GB 内存 | 容器部署；浏览器抓取同时最多开 2 个页面，文字识别一次只做一张，内存峰值约 1.4GB（第 5.2 节） |

- 抓取节点每分钟向网站领一次活：到期要抓的来源和管理员要试抓的来源。抓取节点停了，网站照常能用，只是没有新数据；抓取看板会显示抓取节点多久没来领活。
- 为什么分开：实测 11 所学校和研究所的官网和研招网，香港和上海都能访问（浙大要用 HTTP），但从上海访问快 2–4 倍；浏览器抓取和附件解析吃 CPU 和内存，放在上海也不占网站服务器的资源。判别和抽取都调用外部接口，抓取节点不跑模型。
- **备份**：数据库和快照每天备份，做法参照鼠洞。
- **监控**：除了抓取看板，网站也接入服务器上的监控，和鼠洞一样。
