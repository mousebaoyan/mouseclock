# 鼠钟 · 总体设计

> 状态：草案，待评审。表结构见[数据表](data-model.md)，接口见[接口](api.md)。想法的来源和讨论见鼠洞的[征集意见帖](https://bbs.mousebaoyan.cn/t/6771)。

## 1. 目标

- **不漏截止时间**：自动收集各高校学院官网的保研通知（冬令营、夏令营、预推免、九推），整理出截止时间和要点，快到了提醒。
- **盯着发布**：关注的学院一发新通知就提醒，不用等通知出来再去找。
- **信息可信**：每一项都附原文里的那句话；原文删了也有快照；大家一起纠错，每次修改都有记录，能撤销。
- **快**：页面 1 秒内打开，在手机 QQ 里也流畅；筛选、排序、搜索即时出结果；每天抓几百个来源，也不拖慢网站。
- **好接入**：群 bot 每天发一条汇总；用户自己的 Agent 能直接查询、订阅。

暂不做：把公众号当作来源（第 17 节「以后」），官网的通知链到公众号文章的照常抓（第 7.2 节）；入营、优营名单和考核结果挂在对应的项目上，用来提醒、补上其中的时间，名单上的人不整理成表。

## 4. 架构

```text
抓取节点（上海）
  │  领活 → 抓列表页、正文和附件 ──▶ 学院、研究生院官网（通用 / 配置 / 浏览器 / 专用适配器）
  │  整理成快照 → 初筛：判别模型看标题 → 抽取：LLM 按字段输出，每项附原文证据
  ▼  HTTPS：抓取节点主动连接，用抓取节点令牌
网站（香港，和鼠洞同一台服务器）── 数据库：1Panel 的 PostgreSQL
  ├─ 收结果：存通知和快照，归并成项目和版本，拿不准的进审核页
  ├─ 网页 / API / MCP ◀── 浏览器、用户的 Agent
  ├─ 登录 ──▶ 鼠洞（授权方）
  ├─ 消息和邮件 ──▶ 订阅和关注的提醒
  └─ 群汇总 ◀── AstrBot 插件每天来取
```

- **两个部署单元**：抓取节点负责抓取、初筛和抽取，网站负责其余的一切。两边只通过[抓取节点接口](api.md#6-抓取节点)交接，不共享数据库，可以用不同的语言，各自部署、各自升级。
- **抓取节点不存业务数据**：要抓什么、哪些通知已经见过，都问网站；抓完把结果交给网站。网站连不上时这一轮就等着，下一轮再来。
- **只有抓取节点主动连接**：网站不连抓取节点，抓取节点放在内网也行，只要能访问外网。
- **一套业务逻辑**：网页、API 和 MCP 调用同一组服务函数，权限、订阅上限和修改记录只有一套。
- **不直接连 QQ**：群汇总由 AstrBot 插件定时来取，和鼠洞的做法一样；鼠钟不反向连接插件。

## 5. 技术选型

评判标准：
- 模型写这门技术写得准不准；
- 类型检查快不快、严不严；
- 版本稳不稳；
- 实测性能；
- 优先选主流的；服务器上已有的（1Panel 的 PostgreSQL、Redis）能复用就不加新服务。

### 5.1 选定的方案

| 部分 | 选定 | 理由 |
| --- | --- | --- |
| 网站 | 和鼠洞同一套：TypeScript 7、Node 26、React Router 8、Hono 和 `@hono/zod-openapi`、Kysely、Tailwind CSS 和 shadcn/ui；pnpm、oxlint、Prettier、Vitest、Playwright | 登录、邮件、界面风格和写法都能照搬。选型依据和框架的实测见[鼠洞的总体设计 §5.2](https://github.com/mousebaoyan/mousehole/blob/main/docs/design.md#52-选型依据) |
| 数据库 | 服务器上 1Panel 的 PostgreSQL 18 | 和鼠洞共用实例，不加新服务 |
| 发邮件 | nodemailer，只在 `reminders` 里用 | 和鼠洞一样，SMTP 的主流库 |
| MCP | 官方的 `@modelcontextprotocol/server`（v2），只在 `agents` 里用 | 官方 SDK，只依赖 zod；自带标准的 `fetch` 处理函数，直接挂在 Hono 上 |
| 抓取节点 | Python 3.14，uv 管依赖；Ruff 做 lint 和格式化，Pyright 的严格模式做类型检查，pytest 做测试 | 浏览器抓取、正文提取、PDF 和 Office 解析，Python 的库最全，代价是多一套工具链。Pyright 和 VS Code 的 Pylance 是同一个引擎，编辑器里看到的错误和 CI 一致 |
| 抓取 | httpx（异步）请求网页，Playwright 驱动浏览器（Chromium 的无头精简版），lxml 按 CSS 或 XPath 取出列表 | 各自领域的主流库 |
| 正文和附件 | 正文按建站系统的模板用 lxml 取；pypdf 读 PDF，python-docx 读 `.docx`，legacy-doc 读老的 `.doc`，openpyxl 读 `.xlsx`，xlrd 读 `.xls`；图片和扫描的 PDF 交给 LLM 读，扫描的 PDF 由 pypdf 取出每页的图片，Pillow 把长图切成小块 | 都关在 `parse` 模块里，换了不影响别处。正文和附件用真实的通知和附件比较后定，结果见第 5.2 节。不用 AGPL 许可的 PyMuPDF |
| 接口的类型 | 网站用 Zod 写接口的定义，生成 OpenAPI 文档；抓取节点从这份文档生成 Pydantic 模型 | 两边语言不同，接口的类型也只有一个来源。抓取节点用 Pydantic 校验网站的返回和模型的输出 |
| 判别接口和 LLM | 都用华东师大开放平台：判别用 `ecnu-decision`（System One 接口）；LLM 用 `ecnu-max`，就是 DeepSeek V4.1 Flash，按编号抽取，也读图片里的文字；核对用 `ecnu-plus`，就是 Qwen3.8 Flash | 判别见第 8.1 节，抽取比较见第 8.5 节，读图和本地文字识别的比较见第 5.2 节，核对见第 8.3 节。LLM 走平台的 Chat Completions：它的 Responses 接口收下 JSON Schema 却不按它输出 |

### 5.2 实测

测试机：AMD Ryzen 7 8845HS，Chromium 156（Playwright 1.64），Python 3.14。

**总表一次发给浏览器**（第 14 节）：造一年的项目（200 所学校、600 个学院），只带总表要用的字段；在 Chromium 里解析，按全部筛选条件和关键词筛一遍，再按截止时间排序。手机用 CPU 降速模拟。

| 项目数 | JSON | gzip | Brotli（质量 5 / 11） | 降速 6 倍：解析 + 筛选排序 |
| --- | --- | --- | --- | --- |
| 1000 | 401KB | 62KB | 54KB / 42KB | 3.7ms + 1.3ms |
| 3000 | 1045KB | 165KB | 138KB / 105KB | 8.5ms + 3.8ms |
| 6000 | 2009KB | 321KB | 265KB / 200KB | 14.9ms + 9.3ms |

CPU 不是问题，要省的是带宽，做法见第 14 节。

**浏览器抓取**：用 Chromium 的无头精简版，不加载图片、字体和音视频。

| 测了什么 | 结果 |
| --- | --- |
| 内存（浏览器加 Playwright 的驱动） | 空载约 210–240MB；开一个页面峰值 370–450MB，看页面大小；同时开两个列表页约 410MB。完整版 Chromium 的无头模式空载就要 330MB，峰值 520MB |
| 厦大信息学院的列表页 | 浏览器 0.7 秒；普通请求 0.22 秒、39KB，标题都在 HTML 里，用不着浏览器 |
| 电科计算机学院 | 用了瑞数的反爬：先返回 202 和一段脚本，脚本设好 Cookie 后重新请求。Playwright 默认带着自动化标记（`navigator.webdriver` 为真），无头模式的 UA 里写着 `HeadlessChrome`，有一处就返回 400；关掉自动化标记、UA 里写成 `Chrome` 就能通过，UA 末尾照样写明鼠钟。首页 3.1 秒，内存峰值约 425MB；同一个会话里再开列表页，不用再过挑战 |

**正文和附件**（2026-11-09）：45 个来源各取 2 条最新的通知，加上中科院几个所的 7 条，共 97 页；从中下载 35 个附件，PDF、Word、Excel 都有。

| 测了什么 | 结果 |
| --- | --- |
| 取正文 | trafilatura 遇到正文只有一个嵌入 PDF 的页面（东南大学的 WebPlus）、正文是一张图片的页面（北邮），会把导航和页脚当成正文；找「文字最多的一块」，83 页里有 19 页认成了页脚或翻页。按建站系统的正文容器取（博达、WebPlus、TRS、GPower，加上北科研究生院和国科大的几种），97 页都认得出 |
| PDF | pypdf 和 pdfplumber 在 8 个 PDF 上取出的汉字一个不差；pypdf 把表格的一行留在同一行，pdfplumber 会把折行的单元格拆开；pypdf 快两三倍（89 页 0.97 秒对 2.89 秒，Apple M4）。东南大学的两个 PDF 把常用字映射成样子相同的康熙部首（「⽣」代替「生」），取出后换回常用字 |
| Word | python-docx 按段落和表格的顺序取 `.docx`，表格一行一行，横向合并的单元格只取一次。90 页通知里的 90 个附件链接（不算正文里的图片）有 26 个是老的 `.doc`，多是申请表：legacy-doc（纯 Python，MIT 许可）读的 7 份里，6 份和 LibreOffice 导出的汉字一致，剩下一份 LibreOffice 丢了整张表格，它取全了。它没带类型标注，`crawler/typings/` 里补了用到的部分。另一种做法是镜像里装 antiword（2005 年后没人维护）或 LibreOffice（几百 MB） |
| Excel | openpyxl 读 `.xlsx`，xlrd 读 `.xls`，样本里各 1 个都没问题 |
| 下载 | 7 次拿到的不是文件，是博达的「请输入验证码下载附件」页面（北科计通、厦大、电子科大信通、国科大杭州等）；先打开通知页、带着来源页下载也一样，是网站的设置。按第 7.2 节不破解：附件照样列出，文字留空，不存文件 |

**图片里的文字**（2026-11-14）：从 `data/sources.csv` 的 9 个来源各取一张通知图片（截图、海报、长图、密集的日程表），比较本地的文字识别 RapidOCR 和让 DeepSeek 的 `deepseek-flash` 直接读图。只看日期、时刻、网址和邮箱：同一行里和原文一字不差才算对，一张里错一项就不算全对；9 张共 113 项。

| 读法 | 认对 | 全对的图片 | 每张耗时 | 每张 token（输入／输出） | 每张费用（高峰时段） |
| --- | ---: | ---: | ---: | ---: | ---: |
| RapidOCR | 94/113 | 4/9 | 约 18 秒 | — | — |
| DeepSeek，整张送 | 95/113 | 4/9 | 3.7–9.6 秒 | 约 1070／1120 | 约 0.0017 美元 |
| DeepSeek，切块送 | 111/113 | 7/9 | 3.7–8.1 秒 | 约 6260／1140 | 约 0.0032 美元 |

- RapidOCR 用几种设置里最好的一种：PP-OCRv6 small，在缩小的图上找行，从原图上一行一行切下来认。耗时和内存是在限成 4 核、3600 MiB 的 Linux 容器里测的，一次认一张，峰值约 750 MiB；更大的 medium 模型单独就要占 3.3 GB，抓取节点放不下。
- DeepSeek 会把每张图缩到约 1300×1300 像素以内（最多 1024 个 token），长图缩下去字就太小。切块送：尽量在没有字的行把长图切开，每块不超过约 1300×1300 像素，按从上到下的顺序每 2 块放在一次请求里，说明是同一张图切开的几段，各次读出的文字按顺序接起来：几百行的名单一次全送，会超出 16384 token 的输出上限，平台慢的时候也会超过 180 秒的超时（2026-11-17 北邮信通院的两张复试名单，31 块和 14 块：4 块一次时每次 2200–5500 token，最慢的超过 180 秒；2 块一次时每次最多约 3200 token，最慢 90 秒）。透明背景的图先铺上白底再切：透明的像素自带颜色，常是黑的，不铺就成了黑底黑字，模型只会写 □ 或者陷进重复。提示词要求一字不差地照抄，不改字、不纠错、不补全，看不清的写 □；温度 0，不开思考。费用按官方价格和实际用量算，低谷时段减半。

三种读法错的样子不一样：

- **RapidOCR**：两行认成了乱码，一行整个漏掉，日程表里的日期和时刻拆到了两行，两个网址断成两截；也有看着像对的：`logon` 认成 `1ogon`，`_` 认成 `-`，`https` 认成 `htps` 或 `http`，网址末尾的 `/` 丢了。
- **整张送**：没有乱码，错的都看着像对的。字太小时它照着上下文猜：改日期（`9月17日` 写成 `8月17日`），认错网址和邮箱里的字母，或者换成相近的（`logon` 写成 `login`，导师名单的网址换成了别的页面，邮箱换成同一页上的另一个），还编了一整句原文里没有的话；另把日程表里 5 处全角冒号写成了半角。
- **切块送**：错 2 项，都是网址里多了一个字母或一个点（`dsjies` 写成 `dsjjies`，`ssyjsbm` 写成 `ssy.jsbm`），也是看着像对的。

**同一张图每次读的不一样**：温度设成 0，再读一次文字也可能不同。三张切块再读一次：西电那张一字不差（还是错在 `dsjjies`）；电子科大计算机学院那张只是日程表里两行的换行不同；电子科大信软学院那张，第一次读对的两处 `yzbm.uestc.edu.cn` 这次读成了 `yzb.uestc.edu.cn`。几小时内再送同一张图，输入有 97% 命中缓存，这三张再读一次每张约 0.0017 美元，不到第一次的一半。

图片和扫描的 PDF 改由 DeepSeek 切块读：认对的多 17 项，没有乱码和漏行，抓取节点也不用再跑识别模型。代价是每张约 0.0032 美元，以及读出的文字不稳定、错了也像对的：

- 读过的文件存在抓取节点上，文件没变就用上次的文字（第 7.4 节）。不然没截止的项目每天重抓通知时，有图片的通知天天出一份新快照、再抽取一次，修改记录里还会出现来回变的网址。
- 图片里读出的关键信息仍可能错，不能当作可靠的原文，证据出自图片的字段交给人审核（第 8.3 节），不根据上下文猜。

**扫描的 PDF**：PDF 的某一页取不出文字，就用 pypdf 取出这一页上的图片，和别的图片一样交给 DeepSeek 读，不另加渲染页面的库：扫描件一页就是一张图片，取出来的就是扫描时的原图。扫描件很少见：从 45 个来源最近的通知里取到 13 个 PDF，又从网上搜到 13 个高校推免通知的 PDF，全都有文字层。把其中 8 份的前两页渲染成三种扫描件（彩色 JPEG 200 dpi、黑白 300 dpi、页面转了 90 度）试过，pypdf 都取得出图片，转过的页面取出的是没转回来的图片；当时是用 RapidOCR 认的，换成 DeepSeek 后没有另测。用 JBIG2 压缩的黑白扫描件，pypdf 要另装 AGPL 许可的 jbig2dec 才能解开，镜像里不装，这种文件和别的坏附件一样记一条日志、文字留空。

## 6. 账号与权限

### 6.1 登录

- 用鼠洞账号登录，鼠洞做授权方，按 OAuth 2.1 授权码流程加 PKCE，步骤见[接口 §2](api.md#2-鼠洞登录)。鼠钟是鼠洞登记的自家应用，不弹授权确认。
- **自动登录**：没有鼠钟会话的人打开页面时，鼠钟把浏览器带到鼠洞。已经登录鼠洞的，鼠洞直接带着一次性凭证跳回来，不用点；没登录鼠洞的回来按访客显示，点「登录」再走鼠洞的登录。
- **不共用 Cookie**：鼠洞的会话只发给 `bbs.mousebaoyan.cn`，鼠钟用自己的会话。这样鼠钟出了问题，也拿不到鼠洞的会话。
- **拿到的资料**：鼠洞的用户 ID、名字、头像、等级、角色、禁言和冻结状态，以及 QQ 号（只用来发邮件，不显示）。每次登录时更新；登录着的人，以及不打开网页也在用鼠钟的人（有订阅、关注或个人令牌的），每小时从鼠洞刷新一次，所以在鼠洞被禁言、冻结或者降级，最多一小时后在这里生效。被封禁的，鼠洞那边的令牌失效，鼠钟让他退出，个人令牌一起作废，也不再给他发消息，等他重新登录。
- 鼠洞的授权接口见鼠洞的[接口 §8.3](https://github.com/mousebaoyan/mousehole/blob/main/docs/api.md#83-oauth-授权)。本地开发和测试用假的鼠洞，也可以对着本地跑的鼠洞（[开发约定 §5](development.md#5-测试)）。

### 6.2 权限

| 谁 | 能做什么 |
| --- | --- |
| 访客 | 看总表的前 5 条预览 |
| 成员 | 看全部；订阅、关注、记报名、贴学院标签、反馈、提修改申请、求收录、生成个人令牌 |
| L3 及以上 | 以上都能，还能直接修改、审核修改申请、标记已核对 |
| 管理员 | 以上都能，还能复核争议、删除项目、撤销某人的全部修改、收回和恢复某人的修改权限、处理求收录、删乱贴的学院标签，管来源、院校清单和学院标签的预设 |
| 站长 | 系统设置：发信邮箱、每类消息的邮件规则、抓取节点令牌 |

- 成员就是鼠洞的成员，也就是在群里的人。冻结的按访客算；禁言的能看、订阅、关注、记报名，也能管自己的邮件提醒和个人令牌，贴标签、反馈、修改、求收录和同求都不能做。
- 鼠洞的管理员和站长，在这里也是管理员和站长。
- 管理员可以单独收回某人在鼠钟的修改权限，不影响他在鼠洞的权限。

## 7. 抓取

### 7.1 来源

- 一个来源是一个通知列表页，比如学院官网的「通知公告」、研究生院的「招生信息」。一个学院可以有几个来源。
- 来源由管理员接入。群友在「求收录」里给的链接只当线索（第 10.1 节）。
- 接入时往回翻页，补上前两年的通知，作为往年数据。
- 只发保研通知的列表，比如研究生院的推免专栏，管理员勾上「全收」：初筛不挡它的通知（第 8.1 节）。

### 7.2 怎么抓

| 方式 | 用在哪 | 接入要做什么 |
| --- | --- | --- |
| 通用抓取 | 列表页规整的，希望是大多数 | 只填通知列表页的地址 |
| 配置 | 结构特殊的 | 几行配置，指明列表、标题、日期和翻页在哪 |
| 浏览器抓取 | 要执行 JS 才能看到内容的 | 用浏览器打开再抓 |
| 专用适配器 | 前三种都不行的极少数网站 | 单独写代码 |

- **按建站系统做模板**：不少高校官网用的是同几家建站系统，一个模板能管一批。通知的正文也按建站系统的正文容器取；哪个系统都对不上的，这条通知记成「认不出正文」，补上那个系统的模板，不猜哪一块是正文。
- **LLM 只在接入时用**：管理员在网站上填好列表页的地址，点「试抓」；抓取节点下一次领活时领到它，有配置就按配置读，没有配置就先通用解析，取不到条目再让 LLM 认出列表、标题、日期和翻页在哪。生成的配置要在抓到的页面上实际读出条目，才交回网站供管理员采用；流程见[开发约定 §2.2](development.md#22-试抓)。管理员看过没问题再保存；之后每天按配置抓，不再问 LLM。
- **试抓的流程**：管理员在来源管理页的表单里填好网址（以及要不要浏览器、已有的配置），点「试抓」，网站记一条试抓；页面显示「等抓取节点」，每隔几秒刷新，直到抓取节点交回结果。结果列出抓到的条目（标题、链接、日期）和生成的配置，失败的写原因。管理员看过点「采用」，网址、要不要浏览器和生成的配置填回表单，再保存来源：采用就是保存来源，配置改前改后记进操作日志；发起试抓也记一条。
- **不硬闯**：要登录才能看的、有验证码的不抓，标成「暂时抓不了」并写明原因。只要求用浏览器打开的脚本挑战（比如瑞数的反爬）不算：页面是公开的，人用浏览器打开就能看，浏览器抓取按[开发约定 §2](development.md#2-抓取和判别)的设置通过，UA 照样写明鼠钟。
- **已经遇到的**：电科计算机学院的官网用了瑞数的反爬，要用浏览器抓取（第 5.2 节）；浙大计算机学院的 HTTPS 连不上，只能用 HTTP，要写进配置。
- **链到公众号文章的通知**：有的学院在官网的通知列表里直接链到自己公众号的文章（北科计算机与通信工程学院的夏令营）。普通请求会被转到微信的验证码页，浏览器打开不用过任何验证，所以 `mp.weixin.qq.com` 的网址不论来源要不要浏览器，都单独开一个浏览器页面打开；正文按建站系统模板认 `rich_media_content`，图片的地址在 `data-src` 里，用普通请求就能下载。

### 7.3 频率和礼貌

- 每个来源每天抓一轮，北京时间 18 点开始：学院的通知多在白天发，傍晚抓一次当天的就都在了；模型平台工作日 8 点到 18 点是高峰，价格翻倍，18 点以后是低谷。
- 同一个网站同一时间只发一个请求，两次请求之间隔 5 秒；请求头写明是鼠钟，附上联系方式。浏览器的一次页面访问算一个请求。
- 不读 robots.txt：抓的都是公开的通知列表，礼貌靠上面这几条保证；有的学院官网一请求 robots.txt 就断开连接（比如西电），照它的规矩反而一页都抓不了。
- 抓源站失败了等下一轮再抓，一轮里不重试。模型平台偶尔成批返回 429 和 5xx，几分钟内就好，这样的调用隔 10 秒、30 秒各再试一次。

### 7.4 发现变化

- **新通知**：列表里出现没见过的链接，直接比网址。
- **正文变化**：还没截止的项目，每天重抓一次它的通知，在它的来源那一轮里一起抓；正文或附件的文字和上一份快照不同，或者附件改成了从图片读的（证据要审核，第 8.3 节），就存一份新快照，再交给抽取。
- **删除**：重抓时通知打不开（404、410），标成「原文已删除」，快照照样能看。从列表里消失不算：列表会翻页，旧通知本来就会被挤下去。
- **附件**：正文里和正文旁附件区里的文件（PDF、Word、Excel、压缩包），以及正文里的图片，按出现的顺序下载下来、取出文字；图片和扫描的 PDF 交给 DeepSeek 读（第 5.2 节），压缩包不取文字。附件和正文一起存进快照。下载不成的（比如要验证码才能下载）和超过 10MB 的，照样列出名称和网址，文字留空：超过 10MB 的读到 10MB 就停下，不整个下载（用浏览器抓的网站，附件由浏览器整个读完，靠超时限住）；DeepSeek 没读成的（接口出错、超时），这条通知这一轮算没抓成，下一轮再抓。
- **读过的文件不重读**：DeepSeek 读同一张图，每次读出的文字可能不同，通知没变也会被当成变了。所以抓取节点把要 DeepSeek 读的文件（图片、有扫描页的 PDF）连同读出的文字存在自己的磁盘上（SQLite），按附件的网址找：再下载到的文件和存着的一个字节都不差，就用上次的文字，不再读；30 天没用到的删掉。存的东西丢了也没关系，只是每个文件多读一次。

### 7.5 抓取看板

- 记下每个来源每一轮的结果：成功还是失败、失败原因（超时、403、找不到列表）、列表里有几条、新通知几条、其中有用的几条，以及 LLM 用了多少 token。
- 连续 2 轮失败的标红；旺季里 30 天没有新内容的标黄，往往是网站改版了，配置抓不到东西。
- 登录后都能看。
- 按天看（北京时间，默认今天），列出这一天抓过的来源，标红、标黄的排在前面：
  - 每个来源一行：学校、学院和栏目，这一天各轮的结果，没抓成的通知能展开看网址和原因，以及这一天的用量。
  - 标红：到这一天为止最近的 2 轮都没读到列表。标黄：这一天在旺季（3–9 月、12–1 月），这个来源 30 天里没有新通知（按第一次见到的时间）。
  - 最上面是这一天按用途和模型的总用量，以及抓取节点上次来领活的时间：抓取节点每分钟来一次，超过 10 分钟没来就提示。
- 来源管理页上每个来源的最近一次结果，链接到那一天的看板，只看这个来源。

## 8. 判别与抽取

### 8.1 初筛

- 新通知先由华东师大开放平台的 `ecnu-decision` 判别模型只看标题，门槛为 0.5，判断是不是保研招生相关的通知：冬令营、夏令营、预推免、九推的报名通知，它们的补充、延期通知，以及入营、优营名单和考核结果。
- 调用 System One 判别接口，现在用华东师大开放平台的，上线初期免费：对带类型的问题（是否、单选、打分）一次给出校准过的概率，快而便宜。[OneJev](https://github.com/OmniJev/OneJev) 兼容同一种接口，需要时也能自己部署；换哪家只改配置。
- 门槛宁低勿高：漏掉一条通知的代价，比多调一次 LLM 大得多。
- 用 `crawler.screening.evaluate` 在标注集上取零漏检的最高门槛，再向下留余量并写明幅度：`ecnu-decision` 在 1,354 条的标注集上（全收的列表不算）从 0.621 取 0.5，留 0.121。换模型时门槛一起重定，标注集扩充后也重跑。
- **全收**：只发保研通知的列表上，有的通知标题不提推免，只看标题判断不出来，比如北科大研究生院「活动安排」里的工程硕博士专项招生办法。这样的来源由管理员勾上「全收」：新通知照样打分、记下分数，但不论分数都送去抽取；定门槛时不算这些列表。勾上以后只管新通知，以前挡掉的不重新初筛。
- 判别接口不可用时，这一轮的初筛等着，不跳过初筛直接送给 LLM。
- 鼠洞的 bot 插件试过用 OneJev 筛群聊：有内容的和闲聊的分数混在一起，定不出门槛。通知标题短而规整，预计会好很多，但要用实验证明（第 8.5 节）。

### 8.2 抽取

程序能取的先由程序取：正文和附件的文字按句编号，日期的写法找出来、换算成时间值，链接和邮箱也都编上号。模型只做程序做不了的判断，比如通知涉及哪几个项目、哪个日期是报名截止、哪个链接是报名入口：它从编号里选，证据写句子的编号，原文由程序取出。

抽取前，网站给出这所学校在院校清单里的学院和近期的项目（编号、学院、届、类型、名称、报名时间），模型对照着认。一条通知的抽取结果是它涉及的项目，一个都没有就是无关：

| 项 | 说明 |
| --- | --- |
| 项目 | 是已有的哪个项目，给出编号；没有就新建 |
| 学院 | 从院校清单里选。联合举办的归发通知的学院，全校统一的归研究生院 |
| 届 | 见第 9.1 节 |
| 类型 | 冬令营、夏令营、预推免、九推，归类见第 9.1 节 |
| 名称 | 照通知的写法，比如「2026 年“智能与网络”夏令营」「推免预报名（第二批）」 |
| 作用 | 这条通知对这个项目是报名（招生简章、报名通知、实施细则）、补充（延期、更正、补充说明），还是名单（入营、增补、优营、复试、拟录取名单，以及和名单一起发的安排） |
| 字段 | 通知里写了的字段，见下表 |

- **项目怎么分**：有自己报名时间的一批报名是一个项目，第二批、增补报名都单独算；报名只有一次、复试分几批的，还是一个项目。分方向或分营的，报名时间各不相同就各算一个，共用一次报名就算一个，方向写进招收专业。
- **一条通知可以涉及几个项目**，比如研究生院的一条通知里有几个学院各自的夏令营，或者优营名单和预推免报名发在一起。

| 字段 | 键 | 值 |
| --- | --- | --- |
| 报名时间 | `apply` | 开始 `start`、截止 `end`，都是时间值；额满即止、先到先审的加上 `"rolling": true`。截止是完成报名的最后时间：网上报名或者发送材料，以通知里主要的那一步为准，别的截止写进其他时间 |
| 报名入口 | `apply_url` | 报名系统的网址；发邮件报名的写 `mailto:` 地址 |
| 活动时间 | `event` | 开始 `start`、结束 `end`，都是时间值，只有一天的两个相同；线上 `online`、线下 `offline` 还是都有 `hybrid`，写在 `mode`；地点 `place`。夏令营是营期，推免是复试或考核 |
| 其他时间 | `dates` | 材料截止、导师推荐、公布名单、确认参加等，每项有名称 `label` 和 `start`、`end` |
| 招收类型 | `degrees` | 硕士 `master`、直博 `direct_phd`，可以都有 |
| 招收专业 | `majors` | 专业或方向，一条一项，照原文 |
| 报名要求 | `requirements` | 排名、外语成绩等，一条一项 |
| 要交的材料 | `materials` | 申请表、成绩单、推荐信等，一条一项 |
| 考核方式 | `assessment` | 笔试、机试、面试等，一条一项 |
| 名额 | `quota` | 照原文，比如「100–150 人」 |
| 待遇 | `benefits` | 路费、住宿、补贴等，一条一项 |
| 联系方式 | `contacts` | 邮箱、电话、QQ 群，一条一项 |

- **分段活动**：共用一次报名的项目，`event` 从最早的开始写到最晚的结束，线上线下都有的写 `hybrid`，中间各段的时间不用另标。
- **营期范围**：夏令营的 `event` 以通知写的营期为准；宣讲、科研实践等另列时间的环节写进 `dates`，不扩展营期。
- **活动时间的精度**：「9 月 19–20 日择期」按这两天的区间写；只给一个活动时间（如「9 月中旬面试」）时，`start` 和 `end` 写同一个时间值；只给最后一批时间时只写 `end`，只写「几点开始」「几号报到」时只写 `start`，不补另一端。
- **滚动报名**：「随时报、随时面、随时录」按先到先审处理，在 `apply` 中加 `"rolling": true`，截止仍照原文写。

- 每个字段附上证据 `evidence`：原文里支撑它的一句或几句，每句写成 `{"quote": "…"}`，在附件里的加上附件在快照里的序号 `attachment`（从 0 开始）；再给一个 0 到 1 的置信度 `confidence`。
- 只给通知里写了的字段，写着「另行通知」的也不给。模型选了字段却什么都没填的，比如开始、截止都空着的报名时间，程序当作没给；招收类型和文字列表里同一项给了两次的只算一次。后来的通知没提到的字段，保持原来的值（第 8.4 节）。
- 附件（申请表模板等）不算字段，详情页直接列出快照里的附件。
- 字段以后可以加，加的时候在这张表里写明值的格式。
- 原文明示了时间、程序却没有对应的日期候选时，模型照抄时间文字并选证据句子编号，交到项目的 `unresolved_dates`，包含目标 `field`、原文 `text` 和程序还原的 `evidence`。目标为 `apply.start`、`apply.end`、`event.start`、`event.end` 或 `dates`，同一端点不同时交推测的换算值。原文没写或另行通知不算未识别时间。
- 学院与已有项目从网站提供的清单中选编号；同一个已有项目只能选一次。选的已有项目和模型给的学院、届或类型对不上的，当作新项目交给网站：模型常把同一系列另一年的项目当成这一个，两者名称只差年份，届则照通知写的给对了；真是已有的项目时，网站会在审核页标出可能重复（第 8.4 节）。对照中的旧时间不作为当前通知的日期候选或证据。

**时间值**：原文写到哪一步就记到哪一步，不替原文补全，都是北京时间。

| 原文 | 时间值 |
| --- | --- |
| 6 月 30 日 23:59 | `{"date": "2026-06-30", "time": "23:59"}` |
| 9 月 19 日 24 点 | `{"date": "2026-09-19", "time": "24:00"}` |
| 6 月 30 日 | `{"date": "2026-06-30"}` |
| 6 月 22 日前 | `{"date": "2026-06-22", "mark": "before"}` |
| 7 月 3 日前后、左右 | `{"date": "2026-07-03", "mark": "about"}` |
| 7 月上旬、中旬、下旬；月初算上旬，月底算下旬 | `{"month": "2026-07", "part": "early"}`，`mid`、`late` |
| 7 月 | `{"month": "2026-07"}` |

- 日期的数字可以用阿拉伯数字或中文数字，比如「二〇二六年六月三十日」「九月中旬」。「号」和「日」等价。完整年月日也接受 `2026-06-30`、`2026/6/30`、`2026.6.30`，同一日期的数字分隔符一致，中间不带空格。数字日期也能带时刻，比如 `2026-6-1 17:00`。
- 日期在括号内、时刻紧跟在括号外时一起识别，比如「（6 月 30 日）17:00」。
- 数字分隔的年月日须包含完整年份。`6.30`、`6/30`、`6-30` 这样的短数字月日按普通文字保留，不论前后写了什么。原文明示的未识别时间走前述 `unresolved_dates` 交接流程。
- 日期与时刻的识别以同一行内的表达式为界，表格跨行的日期和时刻分别保留，同日第二段时间保持原文。
- 日期范围的首端可省略日/号，比如「六月一至三十日」「十二月二十八至一月十日」。没写年份的先按发布年份算，比发布日期早半年以上的算下一年：12 月发的通知写「1 月 10 日截止」算下一年，回顾 7 月的夏令营仍算当年。时间段右端没写的年月跟左端，跨年同样按这条。「即日起」是发布那天；发布日期为空时，要靠它推年份的不给时间值。
- 换算成时刻（排序、倒计时、状态和提醒用）时，拿不准的往早里算：只写到日的截止算到当天结束，带 `mark` 的算到前一天结束，只写到旬或月的算到这段时间开始；开始都从最早的可能算起。页面上照原文的写法显示，不显示换算出的时刻。

### 8.3 校验

网站收到抽取结果时检查，过不了的进审核页，由人判断。模型拿不准的几种先由第二个模型核对，两个模型说法一致的不用人看（见下面「第二个模型核对」）：

- 证据要能在快照里原样找到：在标明的正文或附件的文字里找，只忽略空白的差别。找不到的字段不上表。
- 项目编号要是抽取前给出的项目之一，学院要在这所学校的院校清单里。
- 明显不对的：截止早于发布时间，届不在发布那年到后两年之间。
- 作用是报名、却没有报名截止的，确认原文确实没写；第二个模型也没抽出截止的算确认过。额满即止的本来没有截止，不用确认；抽出了截止、只是截止在等审核的，也不另问，审核的人驳回截止时，原文另有截止的直接到项目页改。
- 证据出自图片或扫描件的字段，第二个模型把图片再读一遍、值也读得出来才直接上表，否则审核通过才上表：这些附件的文字是 DeepSeek 读出来的（第 5.2 节），认错的字在快照里照样原样找得到，看着也像对的。抓取节点交附件时标明文字里有没有从图片读的部分，一份 PDF 只有几页是扫描的也算。
- 置信度低（低于 0.7）的字段，第二个模型独立抽出同样的值才直接上表，否则审核通过才上表。
- 程序认得出的时间不算未识别：整段原文就是程序认出的一个时间，模型却报成未识别的，是漏选了候选；属于其他时间、或者那一端已经选了值的，抓取节点去掉这一条。报名和活动的起止空着的照旧交给人，模型看到了时间却没选上，去掉就漏了；只认出其中一段的（「6月30日后的第三个工作日」）也照旧交给人，前后的字会改变时间。
- 未识别时间的文字及证据在原文中核对后，以 `unparsed_date` 进入审核页，其他确定字段照常处理，对应的旧时间保持不变。审核者在项目页补充时间，再关闭条目；关闭条目本身不会把原文文字换算成时间，也不会覆盖旧值。已有项目即使有旧截止，延期中的新时间未识别也必须入队；同一快照重复交结果不重复入队。

#### 第二个模型核对

抓取节点交结果前，让华东师大平台的 `ecnu-plus`（Qwen3.8 Flash，和 DeepSeek 不是一家，认错和抽错的地方不同，也能读图，价格是 `ecnu-max` 的三分之一）独立核对 `ecnu-max` 拿不准的地方，只在有这些情况时才多调用：

| 拿不准的 | 怎么核对 | 算一致 |
| --- | --- | --- |
| 证据出自图片的字段 | 把证据所在的图片再读一遍 | 时间在第二次读出的文字里也解析得出同一个，文字里的数字（名额、绩点、电话、专业代码）照原样都在，小数点和电话的分段不能变；硕士、直博、线上线下这种选项是模型对文字的理解，不是照抄的字，不核对 |
| 置信度低的字段 | 同样的提示词独立再抽一遍 | 对应的项目这个字段的值完全相同：两次抽取都说是同一个已有项目，或者都说是新的、同学院同届同类型的；哪一次里这样的项目有两个，就分不清，不核对 |
| 报名通知没写截止 | 同上，和置信度低的共用一次 | 对应的项目也没有截止，也没有认不出的截止 |
| 新项目、截止和抽取认的那个项目不同的项目，和学校已有的同学院、同届、同类型的项目 | 分别问两个模型是不是其中一个 | 见第 8.4 节 |

核对的结果随抽取结果交给网站：字段标 `checked`，项目标 `checked: ["no_deadline"]` 或 `["new"]`。网站照旧检查证据能不能在快照里找到、时间明不明显不对；核对调用失败的，照原来的规则进审核页。第二个模型重抽时偶尔选了不存在或不能用的编号，整次重抽不合格，就再抽一次：2026-11-17 用线上 46 份快照试，第一次不合格的 4 份再抽都通过了。

### 8.4 归并与版本

归并在网站上做：要看已有的项目和人工改过的值，这些都在网站的数据库里。网站不调用模型，认项目靠抽取给出的编号。

- 一条通知涉及几个项目，就给每个项目各加一个版本：给了编号的加到那个项目上，没给的新建项目。同一学院、同一届、同一类型已经有项目时，抓取节点先分别问两个模型这是不是其中一个（同一次报名的简章、补充、分批分专业公布的名单都算同一个，另外报名的第二批、专项不算）：都说是同一个，就照那个项目的编号交；都说不是，就标明是新项目；其余新建后在审核页标出来，由人确认。抽取给了编号、通知给的报名截止却和那个项目的不同时，可能是改了时间，也可能是把另一次报名当成了它，也这样问两个模型。模型容易在这几处一起看错，也交给人：名单类的通知总属于某次报名，两个模型都说不是也不算数；报名截止和已有项目相同的，不算不是同一个；两边截止不同的，不算是同一个，抽取给的也是那个项目的除外（改了时间）。
- 项目的名称照建它的那条通知起。由名单或补充通知建出来的项目，第一次有了报名通知时，名称换成报名通知的；人改过名称的不换。
- 版本只带通知里写了的字段：带了的换成新值，没带的保持原样。报名时间和活动时间按开始、截止这些部分合并，比如延期通知只写了新截止，就只换截止，开始照旧；其他时间按名称合并，同名的换成新的，没有的加进去。和原来的值逐个比较，变了的记下来；报名截止变了，订阅的人收到消息（第 11.3 节）。
- 新旧按通知的发布日期比，不按抓到的先后：一个字段的值来自哪条通知，发布得比它早的通知就不改这个字段；后来的通知写了同样的值，来源就换成后来的那条。只写到日、少了时刻的同一天也不改，免得把 12 点的截止换成当天结束；人改的值也一样，这样的值不进审核页。一个来源待抽取的通知按发布日期从早到晚抽，一个项目的通知按发出的先后成为它的版本，第一次往回翻的通知也一样。
- 名单类的版本通常只带时间，比如入营名单里定下的活动日期；名单上的人不整理成表。名单类的版本只补项目还没有的字段，不改已有的值；名单里确认参加、交材料的截止不是报名截止，所以报名时间和报名入口一律不补，只记在版本里。
- 人工改过的字段不会被抓取覆盖。新版本的值和人工改的值不一样时，进审核页。

### 8.6 成本

- 初筛挡掉大部分通知；每条通知只抽取一次，正文变了才再抽。
- 每次调用都记下用量，按天汇总显示在抓取看板上。
- 读图片每张约 3–6.5 credits（按第 5.2 节切块送的用量；平台工作日 8–18 点是高峰，其余时间减半），同一个文件不重读（第 7.4 节）。读图的用量和这条通知的抽取一起交，算作抽取。
- 失败的调用也算：初筛、读图或抽取中途失败的，以及读了图片却不用再抽取的（通知没变），已经花掉的用量随这一轮的抓取记录交给网站。
- LLM 请求按可复用的前缀组织：固定规则与输出结构在前，同一所学校的学院清单和近期项目其次，单条通知的标题、发布日期和编号正文最后。结构化数据使用固定字段顺序，共用部分不加入当天日期、请求编号等易变内容；后续试抓等调用也遵守这条规则。
- 平台自动管理前缀缓存，命中量取 `usage.prompt_tokens_details.cached_tokens`，命中部分按十分之一计费。实验报告保留输入、输出和命中 token，按实际命中计算费用；接口没返回用量或命中数时记为未知，不当作零或免费。
- 估算：一条通知抽取约 1.3 credits（低谷时段，第 8.5 节的复验），高峰翻倍；旺季每天几十条通知进 LLM，一天一两百 credits 以内，在平台每人每 7 天 25000 credits 的免费额度以内。

## 9. 内容

### 9.1 学校、学院和项目

- **学校**：名称、简称和层次。简称可以有几个（北大、PKU），只用来搜索，页面上不显示。层次只记最高的一个：C9 都是 985，985 都是 211，211 都是双一流，记了 C9 就不再记 985；按层次筛选时，选 211 只出现最高是 211 的学校，没有层次的归「其他」。校徽让人一眼认出是哪所学校，项目卡片、院校清单、学院页和项目页上学校名的旁边都有；由管理员上传，存在鼠钟、由鼠钟提供，不从学校的网站去拿，还没有的显示校名的第一个字。
- **学院**：泛指招生单位，包括学院、研究所和研究生院，属于一个学校（中科院的研究所属于中国科学院大学，和研招网上的招生单位一致）。地区记在学院上，是学生就读的地方：深圳校区、中科院的研究所和学校不在一地。院校清单里的学院不一定已经接入来源，没接入的也能关注。
- **项目**：一个学院面向某一届的一次招生活动，分批报名的每批算一个（第 8.2 节）。字段见第 8.2 节，每个字段有值、证据和来源的版本。
- **届**：本科毕业、研究生入学的那一年，和大家说的「27 届保研」一样，按届筛选就能看到这一届能报的全部项目。2026 年的夏令营、预推免和九推是 2027 届，2026 年 12 月到 2027 年 1 月的冬令营是 2028 届。标题里的年份不一定是届：夏令营常写举办的年份，推免常写入学的年份。所以届不让模型判断，由抓取节点按通知的发布日期算：发布那年加一，9 月起发的冬令营加二；抽取时只拿这一届的项目给模型选，免得它把同一系列别的年份的项目当成这一个。
- **类型**：冬令营、夏令营、预推免、九推。各校的叫法不同，这样归类：暑期学校、学术交流营、科学营、开放日算夏令营；学校叫预推免、预报名、提前选拔的推免算预推免，比如电科的「优本计划」；正式的推免招生（招生简章、推免说明）和推免服务系统开放后的补录算九推。普通博士的申请考核、录取后的体检和入学通知、只招已录取博士生的营都不收；学校为本校本科生评定推免资格的推荐办法和推荐名单也不收，它们说的是谁能被推荐出去，不是招谁进来。
- **状态**：按时间算出未开始、报名中、已截止；另有「已核对」和「有争议」两个标记。没写截止的，活动结束算已截止；活动时间也没写的，到这一届推免结束，即前一年的 10 月底，算已截止。

### 9.2 已核对

- L3 以上或管理员核对过一个项目的全部字段后，标记「已核对」，记下是谁、什么时候核对的。
- 之后有新版本改了字段，或者有人修改了项目，标记取消，等再次核对。

### 9.3 学院标签

大家对一个学院的印象，比如对双非友不友好、有没有机试。标签贴在学院上，不随某一年的通知走，往年的评价也算数。

- **预设**：只能从管理员预设的标签里选，用词要中性，不用「歧视」这类字眼，免得引战。每个标签带一句说明，讲清楚贴它是什么意思。先放这几个：

  | 标签 | 说明 |
  | --- | --- |
  | 对双非友好 | 往年有不少双非院校的同学入营、拿到优营 |
  | 卡本科出身 | 往年入营、拿到优营的几乎都是 985、211 的同学 |
  | 看重科研 | 考核看重论文和科研经历 |
  | 看重竞赛 | 考核看重竞赛获奖 |
  | 有机试 | 考核里有上机编程 |

- **贴和撤回**：学院页上列出全部预设，每个旁边写着几个人贴了，自己贴过的高亮；点一下贴上，再点一下撤回，每人每个标签一票。说明在鼠标停在标签上时显示，手机上点「这些标签是什么意思」展开。大家只看得到人数和自己贴了没有，看不到是谁贴的；管理员删乱贴的时候才看得到。禁言的不能贴。
- **3 个人贴了才算**：一个人的看法不当作大家的印象。至少 3 个人贴的，才算这个学院的标签：写在学院页的名称下面和院校清单里，也只有它们能用来筛选；不到 3 个人的，只在学院页的标签列表里看得到人数。
- **筛选**：总表和院校清单都能按标签筛选，可以选几个，选了几个就要同时有这几个标签。
- **删乱贴的**：管理员在学院页上点开一个标签，能看到谁、什么时候贴的，可以删掉其中几票，也可以清空这个学院的这个标签。
- **管预设**：管理员在「管理 · 学院标签」里加标签、改名字和说明、调顺序、删除。改名不影响已经贴的；删除连同大家贴的一起删，删之前提示有多少人贴过。
- 管理员删票、清空和改预设都记进操作日志。

### 9.4 我的报名

一张只给自己看的报名清单：报了哪些项目，走到了哪一步。

- **进度**：想报、已报名、已交材料、入营、优营、未通过、放弃，随时可以改成任意一个，不用按顺序。另外可以写一段备注，最多 1000 字，比如「材料还差推荐信」「导师已回复」。
- **在哪记**：项目页上「订阅」旁边有「记报名」，点开选进度、写备注。总表卡片上，记过的项目底部写着自己的进度。
- **和订阅分开**：记报名不自动订阅，也不占订阅名额；想要截止提醒的，另外点订阅。
- **我的 · 报名**：可以按进度筛选，每个进度旁边写着有几个；按截止排，还没截止的在前。每项写着项目、进度、备注和上次改的时间，进度和备注在原处改；「清除」删掉这一条。
- 只有自己看得到，也不算进任何人数。
- 管理员删掉的项目，记录跟着不显示；两个重复的项目并成一个时（第 12.2 节），记录挪到留下的那个，两个都记了的留后改的那条。
- 冻结的看不到也改不了，解冻后记录还在；禁言的照常能记。

## 10. 页面

- 风格和鼠洞一致；手机优先，兼容 QQ 内置浏览器。标志是鼠洞那只探头的鼠鼠整个爬出了洞，站成一只闹钟：耳朵是两只闹铃，底下是闹钟的脚。
- 筛选条件写在网址里：链接可以分享，用浏览器操作网页的 Agent 也好上手。

| 页面 | 内容 |
| --- | --- |
| 总表（首页） | 项目列表：学校和学院、类型、报名截止和倒计时、订阅人数、原文链接。按届、层次、地区、方向、类型、状态和学院标签筛选；按截止时间、发布时间、订阅人数排序；按学校、学院、项目名和关键词搜索。没选届时显示正在报名的那一届：1 到 10 月是下一年毕业的，11 月起冬令营开始报名，换成再下一届；状态默认只看还没截止的。分页，每页 20、50 或 100 条。访客只看到截止时间最近的 5 条 |
| 详情页 | 最上面是原文链接，下面是各字段和证据、版本记录和每一版的快照、修改记录，以及订阅、记报名、反馈和修改的按钮 |
| 学院页 | 这个学院历年的项目、学院标签、关注按钮和来源 |
| 消息 | 站内消息，点顶栏的铃铛打开（第 11.1 节） |
| 我的 | 订阅、关注、报名、反馈、邮件提醒和 Agent，一样一个标签（第 10.2 节） |
| 抓取看板 | 每天每个来源的结果（第 7.5 节） |
| 修改记录 | 全站最近的修改和撤销，登录后都能看（第 12.4 节） |
| 求收录 | 收录申请、进度和同求人数（第 10.1 节） |
| 审核页 | L3 以上：反馈和修改申请、拿不准的字段和归并、有争议的项目 |
| 管理 | 管理员：来源（接入、配置、试抓）、院校清单、学院标签预设、用户的修改权限；站长：系统设置（发信邮箱、邮件规则、抓取节点令牌） |

### 10.1 求收录

想看的学院还没收录，就提一个求收录；别人提过的点「同求」，人多的先接。

- **在哪提**：顶栏导航里的「求收录」页；院校清单里搜不到时，提示「没找到想要的学院？求收录」；还没接入来源的学院页上也有「求收录」。
- **怎么填**：选学校，再选学院；清单里没有的学校或学院，直接写名字。知道通知列表页的链接可以附上，也可以写几句备注。选的学院已经收录了的，提示一下并链接到学院页；已经有人提过、还没收录的，不另起一条，直接算你同求。
- **同求**：每人一票，可以撤回；提的人自己算一票。关注了还没收录的学院也算一票（第 11.4 节），不用另点，同一个人只算一次；这个学院还没人提过的，关注时就替他新建一条。
- **列表**：分「排队中」「接入中」「已收录」「暂时抓不了」几栏。排队中的按同求人数从多到少排，一样多的先提的在前。每项写着学校和学院、同求人数、什么时候提的和附的链接，自己同求过的高亮；已收录的链接到学院页，暂时抓不了的写着原因。
- **处理**：管理员在列表上改进度：排队中、接入中、已收录，或者暂时抓不了并写明原因（比如要登录才能看、有验证码）；暂时抓不了的以后能接了，再改回接入中。清单里没有的学院，管理员先在院校管理里加上，再把求收录对上它；对上的学院接入了第一个来源，就自动算已收录。重复的两条，管理员可以并成一条，同求合在一起。改进度和合并都记进操作日志。
- **告诉大家**：变成已收录或暂时抓不了时，提的、同求的和关注着的人都收到「求收录有结果」（第 11.1 节）。
- 排队中的求收录没人同求、也没人关注了，就从列表上消失；关注算的那一票，取消关注就撤了。已收录和暂时抓不了的一直留着。禁言的不能提，也不能点同求；关注了照样收消息，但不算一票，也不替学院新建求收录。

### 10.2 我的

从账号菜单进，手机上也在导航抽屉里。一样东西一个标签，每个标签有自己的地址，默认打开第一个：

| 标签 | 内容 |
| --- | --- |
| 订阅 | 订阅的项目，订了几个、最多能订几个（第 11.3 节） |
| 关注 | 关注的学院（第 11.4 节） |
| 报名 | 自己的报名记录，可以按进度筛选（第 9.4 节） |
| 反馈 | 自己提的反馈和修改申请，以及处理的结果（第 12.1 节） |
| 邮件提醒 | 每类消息发不发邮件（第 11.2 节） |
| Agent | 个人令牌、接 Agent 的命令和数据下载（第 13 节） |

哪个功能做好了就加哪个标签。消息不放在这里，点顶栏的铃铛看（第 11.1 节）。

## 11. 消息与提醒

提醒都先进站内的「消息」，要紧的再发邮件。消息说的是鼠钟里和自己有关的事，和学院官网上的「通知」是两回事。

### 11.1 站内消息

- 登录后顶栏右边有一个铃铛，有没看过的消息时带上条数，超过 99 条写 99+。点开是消息页：最新的在前，每页 20 条。
- 每条消息是一行标题、一行说明和时间，点一下就到它说的地方：项目页、学院页、求收录或自己的反馈。
- 打开消息页，页上的就算看过了，铃铛上的数清零；这次新来的几条标着「新」，下次再打开就不标了。打开以后才到的，照样算没看过。
- 消息不能关：不想收，就取消订阅或关注。每类消息发不发邮件可以单独关（第 11.2 节）。
- 冻结的账号不收消息，也不发邮件；禁言的照常收。

| 消息 | 什么时候来 | 例子 | 邮件默认 |
| --- | --- | --- | --- |
| 快截止了 | 订阅的项目截止前 3 天的上午 9 点（第 11.3 节） | 北辰大学 计算机学院「2027 年夏令营」6 月 30 日 17:00 截止，还剩 3 天 | 发 |
| 截止变了 | 订阅的项目的报名截止改了、新定了或者清空了（第 11.3 节） | 北辰大学 计算机学院「2027 年夏令营」报名截止改为 7 月 5 日 17:00，原为 6 月 30 日 17:00 | 发 |
| 学院有新通知 | 关注的学院发了新通知（第 11.4 节） | 北辰大学 计算机学院发了 2 条新通知 | 发 |
| 求收录有结果 | 自己提过、同求过或关注着的学院收录了，或者暂时抓不了（第 10.1 节） | 北辰大学 软件学院已收录 | 发 |
| 反馈有结果 | 自己的反馈或修改申请处理了（第 12.1 节） | 你对「2027 年夏令营」的修改申请已通过 | 不发 |

加一类消息，就在这张表里加一行。

### 11.2 邮件

- 发到 `QQ号@qq.com`。站长没有 QQ 号，不收邮件。
- **每类发不发**：站长在系统设置里给每类消息定邮件的规则：默认发、默认不发、不发。成员在「我的 · 邮件提醒」里没动过的开关跟着站长的默认走，站长改了默认，他们也跟着变；动过的按自己的。定成「不发」的，谁都不发，「邮件提醒」页上也没有这一类。站长没设过时照上表。做法同鼠洞。
- **有消息就发**：要发邮件的消息一来就发一封，不攒着合并。每次发之前按当时的开关和账号状态再看一次，这一类关了或者账号冻结了的，就不发了。
- **内容**：消息的标题、说明和链接；快截止的再附上原文和报名入口。邮件标题就是消息的标题。页脚写明为什么收到，附上「我的 · 邮件提醒」的链接，没登录的点进去会自动登录。样子照[鼠洞的通知邮件](https://github.com/mousebaoyan/mousehole/blob/main/docs/design.md#86-通知与实时)：HTML 加纯文本，不放图片。鼠洞那种不用登录的退订链接要用密钥签名，是新的哈希用途，先不做。
- **发信**：站长在系统设置里配发信邮箱，可以配几个，按顺序用，每个都能发一封测试邮件。一个邮箱发不出去就换下一个；一封邮件发不出去隔一会儿再试，过了一天还没发出去就不发了，站内的消息还在。邮箱的密码用环境变量 `APP_SECRET` 加密后存进库，页面和接口只说设没设过。具体的做法同鼠洞。
- **以后可能限制谁收邮件**：发邮件要花钱，以后可能只发给赞助过的、在鼠洞达到某一等级的，或者用鼠币换了邮件额度的人。所以「这个人能不能收邮件」只在一处判断，现在谁都能；限制只管邮件，站内消息照收；每封邮件都记着发给了谁、什么时候发的，数得出一个人收过几封。真要限制时，「邮件提醒」页上写明为什么收不到、怎样才能收到。

### 11.3 订阅和截止提醒

订阅一个项目，它快截止了、截止时间变了，都会告诉你。

- **在哪订阅**：项目页的名称旁边和总表的每张卡片上都有「订阅」，旁边写着订阅人数；在卡片上点一下就订上了，不用点进项目页。订阅了的写「已订阅」，再点一下取消；没登录的点了先登录。总表可以按订阅人数排序。
- **名额**：同时最多订阅 10 个项目，截止了的也占名额，不再需要的自己取消。满了再订，提示「最多同时订阅 10 个项目」，附上「我的 · 订阅」的链接，那里能一下取消全部已截止的。
- **上限以后可能因人而异**：比如鼠洞等级高的多订几个，或者用鼠币换更多名额。所以每人能订几个只在一处算，现在都是 10；页面上的上限由接口给出，不写死。
- **快截止了**：
  - 截止那天往前数 3 天，上午 9 点提醒，都按北京时间。截止那天照第 8.2 节换算，宁早勿晚：只写到日的、24 点截止的都算当天，「X 日前」算前一天，只写到旬或月的（「7 月上旬」）算这段时间的第一天。
  - 订阅时已经过了提醒的时候、还没截止的，马上提醒一次。
  - 一个截止只提醒一次。截止变了，按新的截止重新算：新的提醒时候还没到，到时候再提醒；已经过了，「截止变了」那条里写着新的截止和还剩几天，就算提醒过了。
  - 额满即止的照样按截止提醒，注明「额满即止，尽早报名」。没写截止的不提醒，等它有了截止，会收到「截止变了」。
- **截止变了**：新通知或者有人修改，改了报名截止，包括从没有到有、从有到清空。按换算出的截止时刻比（第 8.2 节）：只是写法不同、时刻一样的（「6 月 30 日」和「6 月 30 日 24 点」）不算变了。消息写明改前和改后，以及新的截止出自哪条通知，人改的写「人工修改」。改一次发一条，改回去也发；每分钟比一次，一分钟内改了几次的按最后的算。只看报名截止，报名开始和活动时间变了不发。
- **消息里写什么**：学校和学院、项目名、截止和还剩几天。时间照原文的写法，不写换算出的时刻；点进去是项目页，最上面就是原文链接。
- 有争议的项目照常提醒，注明「有争议，请以原文为准」（第 12.3 节）。
- **项目没了**：管理员删掉的项目，订阅跟着去掉，不再提醒。两个重复的项目并成一个时（第 12.2 节），订阅挪到留下的那个，两个都订了的算一个。
- **我的 · 订阅**：订阅的项目按截止排，还没截止的在前，截止了的在后。每个都能取消，已截止的能一下全部取消；上面写着订了几个、最多能订几个。

### 11.4 关注学院

关注一个学院，它一发新通知就知道，不用自己天天去官网看。

- **在哪关注**：学院页名称旁边有「关注」，写着关注人数，不显示是谁；院校清单里每个学院旁边也能直接关注。关注的学院不限个数。
- **哪些通知算**：抽取出了项目的新通知，也就是报名、补充、延期通知，以及入营、优营名单和考核结果；无关的不算。按通知涉及的项目算是哪个学院的：研究生院发的一条通知里有计算机学院的夏令营，关注计算机学院的也会收到。同一条通知对同一个学院只发一次：之后正文改了不再发，同一个网址在别的来源里已经见过的也不再算（同一条通知常常学院和研究生院都发）；订阅了项目的，截止变了另有消息（第 11.3 节）。
- **什么时候来**：一个来源抓完一轮，把这一轮新发现的通知按学院合成一条消息，比如「北辰大学 计算机学院发了 2 条新通知」，说明里列出通知的标题和作用（报名、补充、名单）。只有一条的，点进去是它的项目；几条的，点进去是学院页。抓取在每天傍晚（第 7.3 节），所以这类消息多在傍晚来。要审核以后才归到项目上的（第 12.2 节），审核通过时再补发。
- **往年的不算**：来源第一次抓时往回翻补进来的通知不发消息，那些多是往年的；学院刚收录时，关注着的人收到的是「求收录有结果」（第 10.1 节）。
- **还没收录的学院**：也能关注，关注了就算替它求收录：还没人提的新建一条，提过的算一次同求（第 10.1 节）；禁言的关注了不算。收录以后，新通知照常来。
- **我的 · 关注**：关注的学院按学校排，每个写着这一届有几个项目、最近一条通知是哪天，可以取消；还没收录的标「未收录」，附上它的求收录进度。

### 11.5 群汇总

每天上午 9 点，鼠洞的 bot 插件（[astrbot_plugin_mousehole](https://github.com/mousebaoyan/astrbot_plugin_mousehole)）从鼠钟取一份汇总，发到群里：

```text
鼠钟 · 11 月 18 日
昨天新收录 3 个项目，3 天内截止的有 2 个：
1. 北辰大学 计算机学院「2027 年冬令营」11 月 20 日截止
2. 南屿大学 软件学院「冬令营」11 月 20 日 17:00 截止
https://ddl.mousebaoyan.cn
```

- **新收录**：昨天（北京时间）新建、还没截止的项目，删掉的不算。新接入的来源往回翻补进来的往年项目都已截止，不会算进来。
- **3 天内截止**：按换算出的截止时刻，从取汇总时起 72 小时内截止的项目，不分届，按截止排，最多列 5 个，多的写「还有 N 个」。时间照原文的写法。
- 只带一个链接，是总表：总表默认按截止排、只看还没截止的，正好接着看。
- 两个数都是 0 的那天不发。每天只发这一条，不 @ 人，免得触发 QQ 风控。
- **怎么交接**：鼠钟的 `GET /bot/summary` 返回写好的整段文字，插件原样发出去；没什么可发的 `text` 为 `null`，插件就不发。汇总里的内容和访客在总表上能看到的预览差不多，取的时候不用令牌。插件那边要做的（定时来取、发到哪几个群、和鼠洞的收录汇总怎么排队）在插件的仓库另开 Issue，按它的[防风控](https://github.com/mousebaoyan/astrbot_plugin_mousehole/blob/main/docs/design.md#2-防风控)规则做。

## 12. 纠错、审核与争议

### 12.1 反馈

看到项目里哪里不对，随手就能说。反馈有两种：

- **这里不对**：只说哪里有问题，比如「截止和原文对不上」「和另一个项目重复了」。
- **应该改成**：给出改成什么，也可以是清空，这就是修改申请，要写理由、附依据（原文或截图的链接，或者写明在哪看到的）。填法和直接修改一样，只是提交后要等 L3 以上的人审核。

怎么用：

- **在哪提**：项目页上有「反馈」；每个字段旁边也有一个小的「反馈」，点了就选好了这个字段；报名时间、活动时间这种分几部分的，再选是哪一部分（开始、截止、额满即止……），和直接修改一样按部分算。可以说某个字段，也可以说整个项目：名称、届、类型不对，不该收，或者和别的项目重复了。L3 以上的人点「反馈」时，也可以直接改（第 12.4 节）。
- **不重复提**：项目页上写着有几条待处理的反馈，点开能看到每条说了什么、谁什么时候提的；别人已经说过的问题，就不用再提。同一个人对同一个项目的同一处，同时只能有一条待处理的，再提就是改那一条。
- **撤回**：待处理的可以撤回。
- **项目没了**：管理员删掉的项目，待处理的反馈一起关掉。两个重复的项目并成一个时（第 12.2 节），反馈挪到留下的那个；同一个人对同一处都有待处理的，留后提的那条，先提的那条算撤回。
- **结果**：处理了会收到「反馈有结果」（第 11.1 节），「我的 · 反馈」里列着自己提过的全部反馈和处理结果。
- 禁言的不能提。通过 Agent 也能提（第 13 节），记录里标「通过 Agent」。
- L3 以上可以不提申请，直接修改，同样要写理由、附依据（第 12.4 节）。两种反馈都算进争议的人数（第 12.3 节）。

### 12.2 审核

- **反馈和修改申请**：L3 以上在审核页的「反馈」一类里处理，先提的在前。每条写着项目、说的是哪一处、现在的值和来源、提的人说了什么或要改成什么、理由和依据；提了以后这一处又变过的，标出来，审核的人比一比再定。不能审自己提的。处理完，提的人收到消息。
  - 修改申请：「通过」就照申请改，算一次修改，改的人记审核的人，修改记录里链接到这条申请；「驳回」要写理由。
  - 这里不对：去项目页改好后点「已改正」，或者点「没问题」并写明为什么。
- 抽取拿不准、第二个模型核对后也说不准的字段和归并，和人工改过的值冲突的新版本，也都在审核页处理（第 8.3、8.4 节），按种类分开列，只列有条目的种类。每种开头用一两句话说明为什么要看、怎么判断；每条只问一件事，看得到原文的证据和抽出来的值，证据能直接打开快照里的那句话或所在的附件，在原处点一下按钮就处理完，不用离开列表；点错了 5 秒内可以撤回，过了 5 秒才提交，这之前离开页面的不提交，条目还在。通过的效果如下；驳回只关掉这一条，什么都不改。

| 待审的 | 通过 |
| --- | --- |
| 证据找不到、证据在图片里、置信度低、明显不对的字段 | 照抽出来的值上表，来源记为那个版本，之后的通知照常更新它；值变了的记进那个版本改了的字段。这个字段的值已经来自发布得更晚的通知的，不改（第 8.4 节） |
| 和人工改的值冲突的字段 | 同上：新版本的值替换人改的值 |
| 编号或学院对不上、届不对的项目 | 审核的人从这所学校的项目里选对的那个，或者选对它的学院、届和类型新建一个，再照收抽取结果时那样归并（第 8.4 节） |
| 可能重复的新项目 | 不是重复的就保留；是重复的，选出原来的那个，把这个项目的各版本按顺序并进去（它的字段审过的照审过的结果办，不再问一遍，这些决定也随版本挪到原来的项目上），再删掉这个：它待审的「原文时间无法识别」挪到原来的那个上，其他待审的条目一起关掉；它的订阅、报名记录和反馈也挪到原来的那个上。删掉的这个，链接打开的是原来的那个。有人改过它的字段的，先撤销那些修改再并，并进去以后到原来的项目上重做。两个项目都有同一份快照的版本的（比如同一版通知抽成了两个），并不了，删掉多出来的那个；同一条通知改版后的快照照常能并 |
| 报名通知没有截止 | 确认原文确实没写；原文写了的，去详情页改报名时间 |
| 原文时间无法识别（`unparsed_date`） | 核对日期原文和证据，去项目页补充时间后关闭条目；关闭本身不换算原文、不覆盖旧时间 |

- 字段的条目旁边写着这个字段现在的值和来源：之后有更新的通知或者人改过的，审核的人比一比再决定。
- 每次审核记进操作日志，条目上记下谁、什么时候处理的，通过还是驳回。

### 12.3 争议

一个项目有好几个人说不对，就标上「有争议」，请管理员来看。

- **怎么算**：上次复核以后，有 3 个不同的人反馈这个项目有问题（修改申请也算），就自动标上「有争议」。待处理的和驳回了的都算：驳回了还有人说不对，正是要管理员看的；撤回的、已改正的和通过了的不算。
- 标上以后一直保留到管理员复核，之后有人撤回了反馈也不取消。
- **大家看得到**：项目页最上面写着「有争议：有几个人反馈这里可能有错，请以原文为准」，总表卡片上标「有争议」。
- **提醒照发**：万一信息其实没错，停了提醒反而会让人错过截止；提醒里注明「有争议，请以原文为准」（第 11.3 节）。
- **复核**：有争议的项目排在审核页最前面，单独一类，只有管理员能处理。管理员看过这个项目的反馈和修改记录，改正，或者确认没错，写上说明，再取消标记。这个项目待处理的反馈一起关掉：改正了的算「已改正」或「通过」，确认没错的算「没问题」或「驳回」，提的人收到消息，说明就是处理结果。之后的反馈重新计数。
- 复核记下谁、什么时候、说明，项目页的修改记录里看得到。

### 12.4 记录和撤销

- 每次修改、审核、标记已核对和复核争议，都记下谁、什么时候、通过网页还是 Agent、改了哪个字段、改前改后的值、理由和依据。
- 登录后都能看记录：每个项目的详情页有它的修改记录，「修改记录」页有全站最近的。
- **修改**：一次改一个或几个字段，或者项目的名称、届、类型。报名时间、活动时间和其他时间按部分记，只改了截止就只记截止，没改的部分照常由之后的通知更新。人改过的字段之后的通知不覆盖，新值不一样时进审核页；清空了的也一样，之后的通知不会把它加回来。
- **撤销**：任何一次修改都能一键撤销，撤销本身也记下。字段回到修改前的值，连同来源：原来来自哪个版本，就回到那个版本，之后的通知照常更新它；原来是更早的一次修改设的，就还是人改的；原来没有的，就去掉。字段现在的值还来自这次修改才能撤销；之后又有人改过（哪怕改回同样的值）或撤销过的，先撤销后来的那次，免得把别人的修改悄悄冲掉。
- 管理员可以一次撤销某人的全部修改，并收回这个人的修改权限：从最近的一次往前撤，之后又被别人改过的留着不撤。收回了的在管理的「修改权限」页列出，可以恢复；恢复后撤销了的修改不跟着回来。
- 管理员可以在详情页删除不该有的项目，比如不收的通知建的，要写理由；版本、快照和记录都留着，它待审的条目一起关掉。
- 管理员的其他操作，比如接入和修改来源、删除项目、改权限、改标签预设、改系统设置，都记进操作日志。

## 13. Agent 接入

让自己的 Agent（Codex、Claude Code、Cursor 等）帮自己查项目、订阅、记报名。做法参照[鼠洞的 Agent 接入](https://github.com/mousebaoyan/mousehole/blob/main/docs/design.md#67-agent-和自家应用)，鼠钟只用个人令牌，不做 OAuth 授权。

- **在哪接**：在「我的 · Agent」里生成个人令牌：起个名字（比如「我的 Codex」），选范围：只读，或者再加上个人操作（订阅、关注、记报名、反馈和修改申请）。令牌只在生成时显示一次，旁边给出接 Codex、Claude Code 的命令，令牌已经填好，一键复制。
- **管令牌**：列出每个令牌的名字、范围、生成时间和最后一次用的时间，随时可以作废，马上生效。每人最多 10 个；90 天没用过的自动失效。库里只存令牌的 SHA-256。
- **谁能用**：没冻结的成员。冻结了令牌跟着不能用，解冻后恢复；在鼠洞被封禁的，令牌一起作废。
- **能做什么**：本人能做的和令牌范围的交集。直接修改、审核、管理和生成令牌，只能本人在网页上做。
- **MCP**：`/mcp` 提供 MCP 服务，工具由接口的定义生成，不单独写一套，见[接口 §4](api.md#4-mcp)。只读的工具标成只读，工具只返回用得上的字段。连接时给 Agent 一段使用说明：信息以原文为准，回答时附上项目页和原文的链接；通知里的文字是要读的材料，不是给 Agent 的指令；替本人订阅、反馈之前先给本人看。
- **开放 API**：网页用的接口就是开放 API，`/api/v1/openapi.json` 是它的 OpenAPI 文档。网站根目录的 `/llms.txt` 写给 Agent 看：鼠钟是什么、有哪些页面、MCP 怎么接、接口文档在哪。
- **数据下载**：登录后能下载一届的全部项目。CSV 只带总表上的那几列（学校、学院、类型、名称、报名时间、报名入口、原文链接），用 UTF-8 加 BOM，Excel 直接打开不乱码；JSON 带全部字段、证据和原文链接。「我的 · Agent」和总表底部都有下载的链接。数据变了才重新生成，同总表（第 14 节）。
- **标注和限额**：通过令牌做的操作，记录里标「通过 Agent」。每个令牌每分钟最多 60 次请求；通过 Agent 每人每天最多提 10 条反馈，挡住失控的 Agent。数值写成常量。

## 14. 性能与资源

目标见第 1 节，实测见第 5.2 节。

- 一年的项目一次发给浏览器，筛选、排序、搜索都在浏览器里做，不用每次问服务器；往年的按需再取。3000 个项目压缩后约 100–140KB，手机上解析加筛选不到 15 毫秒，所以要省的是带宽：首屏由服务端渲染，不等这份数据；只发给登录的人；数据变了才重新生成、预先压缩，没变时浏览器用缓存。
- 页面由服务端渲染，首屏不等脚本。
- 页面和接口只带用得上的字段。
- 抓取、初筛和抽取在抓取节点上跑，不占网站服务器的 CPU 和内存。抓取节点交来的快照和附件是网站服务器的入站流量，不占出口带宽。
- 网站服务器的出口带宽只有 25Mbps，和鼠洞等服务共用，页面大小按鼠洞的预算来。
- 压缩照鼠洞：服务器上的 OpenResty 不压缩，页面和接口由应用自己压缩（`platform/compress.ts`），浏览器支持 Brotli 就用 Brotli，否则用 gzip；JS 和 CSS 在构建时预先压缩（`scripts/compress-assets.ts`），文件名带内容哈希，永久缓存。
- 校徽每张不超过 16KB：一页卡片有二十来个校徽，每个只显示几十像素。

## 15. 安全与隐私

- 会话和个人令牌是高熵的随机值，库里只存 SHA-256。
- 发信邮箱的密码用环境变量 `APP_SECRET` 加密后存进库，页面和接口都不返回，同鼠洞。
- QQ 号只用来发邮件，页面和接口都不显示。
- 订阅人数和学院标签只显示人数；报名记录只有本人能看。
- 交给 LLM 和判别模型的只有公开的通知内容，不带任何用户的数据。
- **最小权限**：抓取节点只有抓取节点令牌和模型的 key，拿不到用户的数据；网站没有模型的 key。抓取节点令牌只能调[抓取节点接口](api.md#6-抓取节点)，库里只存 SHA-256。
- **外部内容当作数据**：网页、附件和模型输出都不可信。快照显示前按白名单净化，只留文字、表格和链接，不执行其中的脚本，也不显示图片：显示就会让每个读者的浏览器都去学院的网站加载；附件只作为下载返回，不在浏览器里打开；通知里的文字只作为要读的材料交给模型，写在提示词里的指令和它分开，通知里写的「指令」不起作用。
- 抓取遵守第 7.3 节；不抓要登录才能看的内容，不破解验证码。
- 快照只给登录的人看，始终链接回原文。
- 页面上的站外链接（原文、报名系统）加 `rel="nofollow noopener"`。

## 16. 部署与运维

| 部分 | 放在哪 | 说明 |
| --- | --- | --- |
| 网站 | 香港的服务器，和鼠洞同一台 | 容器部署（`web/deploy/compose.yml`），前面是 1Panel 的 OpenResty；数据库用服务器上 1Panel 的 PostgreSQL |
| 抓取节点 | 上海的机器：4 核、3.6GB 内存 | 容器部署（`crawler/deploy/compose.yml`），挂一个卷存读过的图片（第 7.4 节）；浏览器抓取同时最多开 2 个页面（约 450 MiB，第 5.2 节），3.6GB 内存够用 |

- 抓取节点每分钟向网站领一次活：到期要抓的来源和管理员要试抓的来源。抓取节点停了，网站照常能用，只是没有新数据；抓取看板会显示抓取节点多久没来领活。
- 为什么分开：实测 11 所学校和研究所的官网和研招网，香港和上海都能访问（浙大要用 HTTP），但从上海访问快 2–4 倍；浏览器抓取和附件解析吃 CPU 和内存，放在上海也不占网站服务器的资源。判别和抽取都调用外部接口，抓取节点不跑模型。
- **镜像**：在 `main` 上打 `v1.2.3` 这样的版本标签时，GitHub Actions 构建网站和抓取节点的镜像，推到 `ghcr.io/mousebaoyan/mouseclock-web` 和 `mouseclock-crawler`（标签是版本号和 `latest`）。两个包设为公开，两台机器不用登录就能拉；镜像里没有密钥。机器上只拉镜像，不编译。
- **网站**：`web/deploy/compose.yml` 在服务器上和 `.env` 一起放在 `/opt/1panel/www/sites/mouseclock/`。加入 `1panel-network`，通过容器名连 PostgreSQL；端口只监听 `127.0.0.1:3280`；根文件系统只读，内存上限 512MB，V8 堆 256MB（抓取节点交的附件文件最大 10MB）。
- **数据库**：1Panel 的 PostgreSQL 里的 `mouseclock` 库和同名账号，这个账号只有这个库的权限；迁移在启动时自动执行。
- **反代和域名**：1Panel 里的反向代理网站 `ddl.mousebaoyan.cn`，证书和 HTTP/3 用 1Panel 的站点设置，其余配置见 `web/deploy/openresty.conf`。Cloudflare 上 `*.mousebaoyan.cn` 已经指向这台服务器，仅 DNS，和鼠洞一样。
- **抓取节点**：`crawler/deploy/compose.yml` 和 `.env` 放在上海那台机器的 `/opt/mouseclock/`。停止时等进行中的几轮做完，最多 10 分钟；读过的图片存在卷 `readings` 里，重建容器也不丢。
- **发布**：
  1. 先把线上的库导出一份，做法同鼠洞。
  2. 在 `main` 上打标签并推送，等 release 工作流把两个镜像推到 GHCR。
  3. 两台机器上各自在项目目录里 `docker compose pull && docker compose up -d`。香港那台和鼠洞一样，用空的 `DOCKER_CONFIG` 匿名拉取：root 的 Docker 配置里有一个拉不了公开包的 ghcr.io 登录。
  4. 确认 `/healthz` 返回 200，抓取看板上抓取节点按时来领活。
- **备份**：数据库每天备份，做法同鼠洞：1Panel 的计划任务，本机和 Google Drive 各留 7 份。快照和附件的文件都在库里，一起备份。
- **日志**：两边都只往 stdout 写 JSON 日志，Docker 按 10MB 一个文件轮转，留 5 个。
- **监控**：除了抓取看板，网站的 `/healthz` 也接入服务器上的 Gatus，容器内和经过公网各一条（`web/deploy/gatus-endpoints.json`），加法同鼠洞。

## 17. 路线图

### 一期：能看、能改

抓取节点（抓取含往年、初筛和抽取）、快照和版本、总表、详情页、学院页、抓取看板、鼠洞登录、审核页、修改记录，以及 L3 以上的直接修改和撤销。已经做完。

### 二期和三期：按功能分工

二期是能提醒、大家一起纠错，三期是接入 Agent，现在一起做。下面每一项是一个完整的功能，单独做完就能上线，不用等别的。设计写在表里列的几节，讲的是用的人看到什么、规则是什么；表和接口见[数据表](data-model.md)和[接口](api.md)，没写到的照周围的代码定，在 PR 里说明。各项的进展和谁在做，见置顶的[路线图 Issue](https://github.com/mousebaoyan/mouseclock/issues/2)。

| 功能 | 设计 | 模块 | 大小 | 和别的功能的接头 |
| --- | --- | --- | --- | --- |
| 消息、邮件和订阅 | 第 10.2、11.1–11.3 节 | `reminders` | 大，维护者先做 | 别的功能发消息、加邮件开关、加「我的」的标签，都用它 |
| 关注学院 | 第 11.4 节 | `reminders`，接口和学院页上的关注在 `sources` | 中 | 关注没收录的学院就算替它求收录（求收录）；审核以后才归到项目上的通知要补发（一期的审核） |
| 我的报名 | 第 9.4 节 | `programs` | 小，适合新人 | 合并重复项目时把记录挪过去（一期的审核） |
| 学院标签 | 第 9.3 节 | `programs` | 中 | 总表加按标签筛选 |
| 反馈、修改申请和争议 | 第 12.1–12.3 节 | `review` | 大 | 提醒里注明有争议（订阅）；审核页加反馈和争议两类，合并、删除项目时挪走或关掉反馈（一期的审核） |
| 求收录 | 第 10.1 节 | `sources` | 中 | 同求算上关注（关注学院）；学院接入第一个来源时自动算已收录（一期的来源管理） |
| 群汇总 | 第 11.5 节 | `reminders` | 小 | 插件那边要改的，在插件的仓库另开 Issue |
| Agent 接入 | 第 13 节，接口 §4、§5 | `accounts`、`agents` | 大 | 别的功能的个人操作都要有对应的 MCP 工具 |

- **怎么认领**：见[参与贡献](../CONTRIBUTING.md#怎么找活)。
- **消息、邮件、订阅和「我的」已经有了**：发消息调 `reminders/messages.ts` 的 `sendMessages`，在引起这条消息的事务里调，冻结的账号不收、要发邮件的一起排上；`reminders` 只用到 `programs` 的东西（项目卡片、时间的写法），`programs` 不调 `reminders`，所以别的模块调它都不会循环依赖；订阅、关注这些要知道别处出了什么事，自己去读那边的表，比如订阅每分钟把项目的截止和成员上次知道的比一次。加一类消息，在 `reminders/kinds.ts` 加一项（名称、邮件默认发不发、为什么收到），并在第 11.1 节的表里加一行；加「我的」的标签，在 `web/app/me-tabs.ts` 加一项，路由加在 `app/routes.ts` 的 `me` 下面。
- **接头由后合并的接上**：两个功能要连起来的地方，后合并的那个负责接上，先做的不用替后来的预留什么。比如订阅先合并，提醒里注明「有争议」由后来的反馈加上；关注和求收录谁后合并，谁把关注算进同求；Agent 接入先合并的，后来的功能给自己的个人操作加上 MCP 工具，反过来就由 Agent 接入给已有的加。
- **一期的代码也要接**：合并重复项目（`ingest/review-items.ts`）、删除项目（`programs/service.ts` 的 `deleteProgram`）、审核页和来源管理是一期做好的，表里写着「一期」的，在自己的 PR 里改那里。
- **总表的缓存**：总表数据没变时返回 `304`，变没变看 `programs/service.ts` 的 `tableVersion`。总表带的东西（订阅人数、有争议、学院标签）由哪项加的，哪项就让它跟着变。
- **从鼠洞刷新**：不打开网页也在用鼠钟的人，要每小时从鼠洞刷新一次（第 6.1 节）。有订阅的由消息、邮件和订阅加，有关注的由关注学院加，有个人令牌的由 Agent 接入加，都加在 `accounts` 的刷新里。
- **改同一处的地方各加一项**：消息的类型（第 11.1 节）、「我的」的标签（第 10.2 节）、总表的筛选都是这样；数据库迁移各加各的文件，编号和先合并的撞了就改号。
- 只和自己有关的细节在自己的 Issue 里和维护者定；要改别的功能的设计，先在 Issue 里说。
