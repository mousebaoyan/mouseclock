# 开发约定

写代码时的具体约定，按需阅读。总的规矩见 [AGENTS.md](../AGENTS.md)；表结构的约定见[数据表 · 约定](data-model.md#约定)，接口的约定见[接口 · 约定](api.md#1-约定)。

> 技术栈还没定（[总体设计 §5](design.md#5-技术选型待定)）。定了以后补上目录、命令和各层的具体写法。

## 1. 结构与分层

- 按领域分模块，同一件事的接口、业务逻辑、查询和测试放在一起，改一个功能通常只动一个目录。预计的模块：

  | 模块 | 管什么 |
  | --- | --- |
  | `sources` | 学校、院校清单、来源和适配配置、求收录 |
  | `crawl` | 定时抓取、发现新通知和变化、快照和附件、抓取看板 |
  | `screening` | 初筛：调用判别模型 |
  | `extraction` | 抽取、校验、归并和版本 |
  | `programs` | 项目、字段、已核对、学院标签 |
  | `accounts` | 鼠洞登录、会话、个人令牌、权限 |
  | `reminders` | 订阅、关注、邮件、群汇总 |
  | `review` | 反馈、修改申请、修改记录和撤销、争议、审核页 |
  | `agents` | MCP 服务和 `/llms.txt` |

- 依赖只能单向：页面 → 接口 → 服务 → 数据库。网页、API 和 MCP 都调用服务导出的函数，不各写一套规则。
- 模块之间只通过对方服务导出的函数协作，每张表只由一个模块写入。
- 后台任务（抓取、初筛、抽取、发邮件）和网页分开运行，通过数据库交接，不互相调用。

## 2. 抓取和判别

- 接入来源时按通用抓取 → 配置 → 浏览器抓取 → 专用适配器的顺序试，前一种能抓就不用后一种（[总体设计 §7.2](design.md#72-怎么抓)）。
- 建站系统的模板放在代码里，和它的测试在一起；单个来源的配置存在数据库里，在管理页面改。
- 每一轮抓取都写一条抓取记录，失败也写，写明原因；不吞掉错误，也不在一轮里反复重试。
- 判别模型和 LLM 的提示词放在调用它的代码旁边。输出都按固定的结构解析，解析不了的当失败处理。

## 3. 测试

- 普通的逻辑用单元测试：新通知和变化的识别、时间规范化、证据校验、归并、权限、订阅上限、提醒时间、争议计数、撤销等。
- 建站系统的模板用保存下来的列表页来测。保存的页面只用来测解析，不放正文和附件。
- 判别和抽取的效果不写成单元测试，用标注集评估（[总体设计 §8.5](design.md#85-实验)）。
